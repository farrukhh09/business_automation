# Android Automation Service для Maxim (не MVP)

> **Статус: только проектное описание. Кода нет и в MVP он не пишется.**
> Компонент можно начинать разрабатывать только после выполнения **всех** условий из раздела 3.
> До этого доставки через Maxim оформляются вручную: `MAXIM_MODE=manual`, «Лист для Maxim» в разделе «Доставка» админ-панели.

Основание: SPEC §26–27, §47 (этап 10), §48; контракт `docs/architecture/06-integrations.md` §4; исследование `docs/research/maxim.md` (проверено 2026-09-15).

---

## 1. Зачем это нужно

В ручном режиме оператор переносит в приложение Maxim каждую доставку дня: адрес «откуда» и «куда», телефон получателя, комментарий курьеру, сумму к оплате при получении. Android-помощник мог бы **подставлять эти данные** в приложение Maxim на служебном телефоне и сократить ручной ввод и опечатки.

Помощник **не** принимает решений и **не** оформляет заказы сам: каждый заказ в Maxim подтверждает человек.

## 2. Архитектура

```text
┌──────────────────────┐        ┌──────────────────────────────┐        ┌──────────────────────┐
│   FastAPI Backend    │  HTTPS │  Android Automation Service  │  UI    │  Приложение Maxim    │
│                      │◄───────│  (приложение-помощник на     │───────►│  (com.taxsee.taxsee) │
│  deliveries,         │  pull  │   служебном телефоне)        │ Access-│  на том же телефоне  │
│  route plan,         │        │                              │ ibility│                      │
│  dispatch-sheet      │───────►│  очередь задач → подстановка │        │  человек проверяет   │
│                      │ задачи │ данных → человек подтверждает│        │  цену и подтверждает │
└──────────────────────┘        └──────────────────────────────┘        └──────────────────────┘
          ▲                                   │
          │  отчёт: номер заказа Maxim,       │
          └── данные курьера, ошибка ─────────┘
```

Поток в терминах существующей системы:

```text
Подтверждённые заказы → Delivery (PENDING) → Оптимизация маршрута
  → POST /api/deliveries/{id}/dispatch  (ManualMaximIntegration, статус AWAITING_DISPATCH)
  → Android-помощник забирает задачу (pull) → подставляет данные в Maxim
  → человек подтверждает заказ в Maxim → помощник отправляет отчёт
  → backend: те же правила, что PATCH /api/deliveries/{id} → статус DISPATCHED
```

Ключевые решения:

- **Backend не меняется по сути.** Реализация `MaximIntegration` остаётся `ManualMaximIntegration` (`dispatch_provider = MAXIM_MANUAL`): backend не делает сетевых вызовов к Maxim. Помощник — это инструмент оператора внутри ручного сценария, а не `MaximApiIntegration`.
- **Pull-модель.** Телефон сам опрашивает backend по HTTPS. Входящие подключения к телефону не нужны, работает через мобильный интернет и NAT.
- **Учётная запись Maxim живёт только на телефоне.** В приложение Maxim входит человек; логин, пароль и данные сессии Maxim в backend не передаются и не хранятся.
- **Отказоустойчивость через ручной режим.** Любой сбой помощника (не тот экран, обновилось приложение, капча, нет сети) — задача возвращается оператору, он оформляет доставку вручную по «Листу для Maxim».

## 3. Условия допуска (все обязательны)

| # | Условие | Почему (по `docs/research/maxim.md`) |
|---|---|---|
| 1 | **Письменное согласие Maxim (Taxsee)** на использование программы-помощника для оформления заказов с подтверждением человеком. Запрос — через официальные контакты (раздел 4 исследования: `515@taximaxim.tj`, корпоративный отдел `business@taximaxim.ru`), шаблон письма там же. | Публичная оферта TJ адресована физическим лицам и не разрешает стороннюю автоматизацию; «молчание оферты — не разрешение». Лицензионное соглашение для партнёров запрещает использование приложения способами, «прямо не предусмотренными» (п. 5.2.5), и попытки несанкционированного доступа (п. 5.2.3). «Правила работы сервиса» для TJ не найдены. Риск — блокировка аккаунта. |
| 2 | **Подтверждено, что Maxim (курьер/доставка) работает в Душанбе.** | На 2026-09-15 на официальном сайте в списке городов TJ только Бустон и Худжанд, страница Душанбе отдаёт 404. |
| 3 | **Соблюдение политики Google Play для AccessibilityService.** Помощник не инициирует, не планирует и не выполняет действия автономно; каждое действие запускает человек. Заметное раскрытие в приложении и явное согласие пользователя. При публикации в Play — Permission Declaration Form и одобрение Google. | Политика Google Play: «Any use of the Accessibility API that enables an app to autonomously initiate, plan, and execute actions or decisions is strictly prohibited». Исключение `isAccessibilityTool="true"` — только для приложений для людей с инвалидностью, к нашему случаю не относится. |
| 4 | **Учтены ограничения Android 13+ и верификации разработчиков.** | Android 13+ «Restricted settings»: у приложений, установленных в обход магазина, доступ к специальным возможностям заблокирован, пока пользователь вручную не разрешит «ограниченные настройки». Верификация разработчиков Android: с сентября 2026 — в Бразилии, Индонезии, Сингапуре и Таиланде, **с 2027 года — во всём мире, включая Таджикистан**; установка только от верифицированных разработчиков (исключения: ADB, «advanced flow», ограниченное распространение до 20 устройств). |
| 5 | **Человек подтверждает каждый заказ.** Помощник только подставляет адрес/телефон/комментарий и останавливается. Проверка цены и нажатие кнопки оформления — всегда человек. | Требование исследования (раздел 1, п. 4; раздел 2.3) и политики Google Play. |
| 6 | **Никакого reverse engineering и обходов.** Запрещено: декомпилировать или модифицировать приложение Maxim; перехватывать его трафик; вызывать закрытые эндпоинты (включая `cabinet.taximaxim.ru/Services/Public.svc`); обходить капчу, антифрод и экраны подтверждения; читать данные других приложений. | SPEC §26: «не пытаться обходить ограничения сервиса»; лицензионное соглашение пп. 5.2.1–5.2.3; оферта п. 3.5 (обнаружение несанкционированного доступа). |
| 7 | **Выключатель.** Администратор отключает помощник одним флагом в backend; при отключении телефон прекращает работу с очередью. | Раздел 2.3 исследования. |

Если хотя бы одно условие не выполнено — компонент не разрабатывается и не устанавливается.
Если Maxim предоставит **официальный API** по договору — Android-помощник не нужен: реализуется `MaximApiIntegration` (`MAXIM_MODE=api`).

## 4. Предлагаемый API между backend и Android-сервисом (проект)

> Эндпоинтов ниже **нет** в контракте `docs/architecture/04-api.md` и в коде.
> Перед реализацией контракт дополняется осознанно (API, модель данных, роли) — и только после выполнения раздела 3.

### 4.1 Общие правила

- Префикс `/api/automation`, только HTTPS (тот же `PUBLIC_BASE_URL`), JSON, ошибки в общем формате `{"detail", "code"}`.
- **Аутентификация устройства:** отдельная учётная запись «устройство», не пользователь-оператор. Администратор регистрирует устройство в админ-панели и получает токен устройства (показывается один раз; в БД хранится только хеш). Токен даёт доступ **только** к `/api/automation/*`, отзывается из админ-панели. Потребуются новая сущность (например, `automation_devices`) и настройка-выключатель — изменения контракта.
- **Rate limiting** — отдельный лимит на устройство.
- **Аудит:** каждое действие пишется в журнал заказа (`order_events`, `actor_type` — устройство) и в логи (`automation.task_claimed`, `automation.task_reported`, `automation.device_heartbeat`) без персональных данных сверх id.
- **Идемпотентность:** повторный отчёт с тем же `lease_id` и `result` возвращает 200 и ничего не меняет повторно.

### 4.2 Эндпоинты

| Метод | Путь | Назначение |
|---|---|---|
| POST | `/api/automation/heartbeat` | Телефон сообщает о себе и получает, можно ли работать. |
| GET | `/api/automation/tasks?date=YYYY-MM-DD` | Очередь задач: доставки на дату со статусом `AWAITING_DISPATCH`, в порядке маршрута. |
| POST | `/api/automation/tasks/{delivery_id}/claim` | Взять задачу в работу (аренда на ограниченное время). |
| POST | `/api/automation/tasks/{delivery_id}/report` | Отчёт о результате. |
| POST | `/api/automation/tasks/{delivery_id}/release` | Вернуть задачу в очередь без результата. |

**Heartbeat**

```json
// запрос
{"device_id": "phone-1", "app_version": "0.1.0", "maxim_app_version": "x.y.z",
 "accessibility_enabled": true, "battery_percent": 80}
// ответ
{"enabled": true, "poll_interval_seconds": 30, "min_app_version": "0.1.0"}
```

`enabled=false` (выключатель администратора, отозванное устройство, устаревшая версия помощника) — телефон прекращает опрос задач.

**Очередь задач** — те же данные, что `GET /api/deliveries/dispatch-sheet` и `DispatchResultOut.copy_text` (адрес «откуда/куда», координаты, получатель, телефон, комментарий, сумма к оплате):

```json
[
  {
    "delivery_id": 41,
    "order_id": 128,
    "sequence": 1,
    "desired_time": "18:00",
    "pickup": {"name": "Склад", "address": "…", "latitude": 38.56, "longitude": 68.77},
    "dropoff": {"address": "…", "entrance": "2", "floor": "5", "apartment": "17",
                "landmark": "…", "latitude": 38.57, "longitude": 68.79},
    "recipient_name": "…",
    "recipient_phone": "+992…",
    "courier_comment": "…",
    "cash_to_collect": 150.0,
    "copy_text": "…",
    "lease": null
  }
]
```

**Claim** — ответ `{"lease_id": "…", "lease_expires_at": "2026-09-15T12:10:00Z"}`; 409 `conflict`, если задачу уже взяли (другое устройство или оператор начал оформление вручную в админ-панели). Аренда истекает автоматически (например, через 10 минут) — задача возвращается в очередь.

**Report**

```json
{
  "lease_id": "…",
  "result": "CONFIRMED_BY_HUMAN",
  "confirmed_by": "Имя сотрудника",
  "external_id": "номер заказа в Maxim",
  "courier_name": null,
  "courier_phone": null,
  "error_code": null,
  "error_message": null,
  "occurred_at": "2026-09-15T12:04:31Z"
}
```

| `result` | Что делает backend |
|---|---|
| `PREFILLED` | Промежуточный: данные подставлены, ждём человека. Только журнал. |
| `CONFIRMED_BY_HUMAN` | Человек оформил заказ в Maxim. Применяются те же сервисы и правила, что у `PATCH /api/deliveries/{id}`: `status=DISPATCHED`, `external_id`, `courier_name`/`courier_phone` (если известны), `dispatched_at`. |
| `ABORTED` | Человек отменил оформление. Статус остаётся `AWAITING_DISPATCH`, задача возвращается оператору. |
| `FAILED` | Экран не распознан / ошибка / нет сети. Статус остаётся `AWAITING_DISPATCH`, доставка помечается для внимания оператора, в журнал — `error_code`. |

Дальнейшие статусы (`DELIVERED`, `FAILED`, `CANCELLED`) по-прежнему меняет оператор в админ-панели. Помощник **не** считывает статусы из приложения Maxim и не отменяет заказы: отмена — вручную в приложении, как в `ManualMaximIntegration.cancel_delivery`.

## 5. Android-часть (эскиз, без кода)

- Экран «Очередь на сегодня» — список задач в порядке маршрута.
- Кнопка «Подставить в Maxim» у **каждой** задачи: действие запускает только человек, фоновых автоматических действий нет.
- `AccessibilityService` находит поля ввода на видимых экранах Maxim и вставляет адреса, телефон и комментарий; на экране с ценой и кнопкой оформления **останавливается**.
- Если экран не совпадает с ожидаемым (обновление приложения, капча, неизвестный диалог) — сразу `FAILED` и подсказка перейти к ручному вводу.
- После оформления человек вводит или подтверждает номер заказа Maxim в помощнике — отправляется `CONFIRMED_BY_HUMAN`.
- Заметное раскрытие и согласие при первом запуске; сетевой опрос — foreground service с уведомлением.
- Токен устройства хранится в Android Keystore; данные Maxim помощник не сохраняет и никуда не отправляет.

## 6. Риски

1. **Юридический:** без письменного разрешения Maxim возможна блокировка аккаунта; оферта и лицензионное соглашение ограничительные.
2. **Технический:** обновления приложения Maxim, капча, антифрод и экраны подтверждения цены ломают подстановку; поддержки со стороны Maxim нет.
3. **Платформенный:** политика Google Play, «Restricted settings» Android 13+, обязательная верификация разработчиков с 2027 года.
4. **Бизнес:** работа Maxim в Душанбе не подтверждена; рынок такси города перерегулирован в 2025 году.

## 7. Порядок работ, если условия выполнены

1. Получить письменный ответ Maxim и сохранить его вместе с документацией проекта.
2. Дополнить контракт (`04-api.md`, `02-data-model.md`): устройства, аренда задач, выключатель, журнал.
3. Реализовать эндпоинты `/api/automation/*` с тестами (моки — только в `tests/`).
4. Прототип помощника на одном служебном телефоне, режим «только подстановка».
5. Пилот: несколько дней параллельно с ручным режимом, сверка данных оператором.
6. Решение о постоянном использовании; ручной режим остаётся резервным навсегда.
