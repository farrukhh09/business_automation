# Техническое задание (исходный текст заказчика)

> Этот файл — источник требований для всей разработки. Не изменять содержание требований; уточнения и решения фиксируются в `docs/ARCHITECTURE.md`.

## 1. Цель проекта

Разработать веб-систему автоматизации продаж и обработки заказов для бизнеса по изготовлению домашней выпечки.

Основной канал общения с клиентами — Instagram.

Система должна автоматически:

* отвечать клиентам;
* консультировать по товарам;
* принимать заказы;
* уточнять недостающую информацию;
* определять новых и постоянных клиентов;
* сохранять историю клиентов и заказов;
* отслеживать оплату;
* формировать производственные сводки;
* рассчитывать выручку;
* формировать список доставок;
* оптимизировать порядок доставки;
* формировать ежедневные отчёты;
* передавать диалог оператору при необходимости.

Дополнительно необходимо предусмотреть возможность автоматизации работы с приложением Maxim.

# 3. Технологический стек

## Backend

* Python 3.12+;
* FastAPI;
* SQLAlchemy 2.x;
* PostgreSQL;
* Alembic или Flyway для миграций;
* Pydantic v2;
* Redis;
* Celery или аналогичный механизм фоновых задач;
* JWT для авторизации администратора;
* Docker;
* Docker Compose.

## Frontend

* React;
* TypeScript;
* Next.js;
* современный UI;
* адаптивную вёрстку.

## AI

AI-модуль должен быть отделён от бизнес-логики.

Не помещать всю логику обработки заказов непосредственно в system prompt.

LLM используется для:

* понимания сообщений;
* определения намерения клиента;
* извлечения данных;
* генерации ответа;
* определения языка;
* обработки естественной речи.

Бизнес-правила должны находиться в Python-коде.

# 11. Логика оформления заказа

```text
Клиент: "Здравствуйте, хочу 2 торта на завтра"
AI: "Здравствуйте! Конечно 😊 Подскажите, пожалуйста, какие именно торты?"
Клиент: "Красный бархат и медовик"
AI: "Отлично. Уточните, пожалуйста:
1. На какое время нужны торты?
2. Это будет доставка или самовывоз?"
...
```

После получения всех обязательных данных система формирует предварительный заказ.

---

# 12. Подтверждение заказа

AI никогда не должен автоматически считать заказ окончательно подтверждённым только на основании неполного сообщения. Перед подтверждением показать клиенту:

```text
Проверьте, пожалуйста, заказ:

Красный бархат — 1 шт.
Медовик — 1 шт.

Дата: 16.09.2026
Время: 18:00
Доставка: да
Адрес: ...

Итого: 1500 сомони.

Всё верно?
```

Только после явного подтверждения клиента (`Да`, `Подтверждаю`, `Всё верно`) заказ переводится `WAITING_CONFIRMATION → CONFIRMED`.

---

# 13. Защита от ошибочного подтверждения

Не считать сообщениями подтверждения: `ну вроде`, `наверное`, `может быть`, `посмотрим`, `думаю да`.

Если AI не уверен, необходимо запросить подтверждение ещё раз.

# 14. FAQ

Отдельный раздел в административной панели для управления часто задаваемыми вопросами. Примеры: какие товары есть; сколько стоит; есть ли доставка; где находится самовывоз; какие способы оплаты; за сколько времени нужно сделать заказ; можно ли заказать индивидуальный дизайн; можно ли изменить заказ.

FAQ не должен быть жёстко прописан в коде. Администратор должен иметь возможность изменять вопросы и ответы через панель.

# 15. Каталог товаров

Администратор может: создавать товар; изменять товар; удалять/деактивировать товар; изменять цену; добавлять описание; включать/выключать товар. AI должен использовать актуальный каталог.

# 16. Клиенты

Раздел «Клиенты». Отображать: имя; Instagram username; телефон; количество заказов; общую сумму заказов; дату последнего заказа; статус клиента; историю заказов.

Разделить клиентов на «Новый клиент» и «Постоянный клиент». Новый клиент — клиент без завершённых предыдущих заказов. Постоянный — клиент, который ранее совершал заказ.

# 17. Заказы

Список заказов. Фильтры: дата; статус; оплата; доставка/самовывоз; клиент.

Для заказа показывать: номер заказа, клиент, телефон, товары, количество, сумма, дата, время, адрес, тип получения, оплата, статус, комментарий.

---

# 18. Изменение заказа

Администратор может изменить: товары; количество; дату; время; адрес; комментарий; статус; оплату. Все изменения желательно сохранять в журнале изменений.

# 19. Производственная сводка

```text
Заказы на 16 сентября:

Красный бархат — 5 шт.
Медовик — 4 шт.
Чизкейк — 7 шт.
Капкейки — 36 шт.
```

Периоды: сегодня; вчера; неделя; месяц; произвольный период.

# 23. Доставка

При выборе доставки система должна запросить: адрес; имя получателя; телефон; дату; время; комментарий для курьера. Адрес должен быть сохранён в структурированном виде.

---

# 24. Геокодирование

Адрес преобразуется в координаты (latitude, longitude). Использовать отдельный сервис геокодирования. Обработка ошибок: адрес не найден; адрес найден неоднозначно; несколько вариантов адреса. В случае неоднозначности бот должен попросить клиента уточнить адрес.

---

# 25. Оптимизация маршрута

Для заказов с доставкой на один день сформировать список точек: Склад → Клиент 1 → Клиент 2 → Клиент 3 → Клиент 4. Предусмотреть сервис оптимизации маршрута.

На выходе: порядок доставки; адрес; координаты; время доставки; телефон; комментарий.

---

# 26. Интеграция с Maxim

Создать отдельный интерфейс `MaximIntegration`. Не связывать бизнес-логику напрямую с конкретной реализацией Maxim. Методы: `create_delivery()`, `get_delivery_status()`, `cancel_delivery()`.

Сначала проверить наличие официального API Maxim, позволяющего создавать заказы.

Если официальный API доступен: `Order → DeliveryService → Maxim API → Создание заказа`.

Если API недоступен, не пытаться обходить ограничения сервиса. Резервный режим: `Подтверждённые доставки → Оптимизация маршрута → Список адресов → Оператор вручную вводит данные в Maxim`.

# 27. Автоматизация приложения Maxim

Если потребуется автоматический ввод адресов в приложение Maxim на Android — это отдельный компонент проекта: `Backend → Android Automation Service → Maxim`. Android-компонент может использовать Android Accessibility Service, если это допустимо правилами и техническими ограничениями приложения. Не делать автоматизацию Maxim обязательной частью MVP.

# 30. Передача оператору

Обработать: text; voice/audio; attachments. Каждое входящее сообщение должно:

2. создать клиента, если его ещё нет;
3. сохранить сообщение;

# 38. AI не должен иметь прямой доступ к базе

LLM не выполняет SQL. Схема: `User → AI → Structured Intent → Backend Service → Database → Result → AI → Response`.

```json
{ "intent": "CREATE_ORDER", "product_id": 12, "quantity": 2 }
```

Backend проверяет существование товара и цену самостоятельно.

Обязательно: PostgreSQL; Backend; Admin panel; Customers; Products; Orders; Payment status; Russian language; Tajik language; AI chatbot; Order confirmation; Instagram integration; FAQ; Customer history; Daily reports; Production statistics; Revenue statistics; Delivery addresses; Route optimization; Operator handoff.

# 49. Критерий готовности

1. Клиент пишет в Instagram.
2. Система получает сообщение.
3. Определяет клиента.
4. AI понимает сообщение.
5. AI отвечает на русском или таджикском.
6. Клиент выбирает товар.
7. AI получает товар и количество.
8. AI запрашивает недостающие данные.
9. Создаётся черновик заказа.
10. Клиент получает итог заказа.
11. Клиент подтверждает заказ.
12. Backend переводит заказ в CONFIRMED.
13. Заказ появляется в админ-панели.
14. Клиент появляется в базе.
15. Если клиент уже заказывал ранее — он определяется как постоянный.
16. Сумма заказа автоматически рассчитывается.
17. Администратор видит статус оплаты.
18. Заказы на выбранную дату объединяются в производственную сводку.
19. Заказы с доставкой попадают в раздел доставки.
20. Адреса геокодируются.
21. Система строит оптимальный порядок доставки.
22. В конце дня формируется отчёт.
23. При необходимости оператор может перехватить диалог.

# 50. Главное правило для разработки

1. Проанализировать структуру проекта.
2. Проверить существующие файлы.
3. Не удалять рабочий код без необходимости.
4. Не создавать дублирующиеся модели и сервисы.
5. Следовать принципам SOLID.
6. Разделять бизнес-логику, API, БД и интеграции.
7. Не хардкодить секреты.
8. После каждого крупного этапа запускать тесты.
9. Исправлять ошибки до перехода к следующему этапу.
10. Не имитировать работу внешних API в production-коде.
11. Для внешних интеграций создавать отдельные адаптеры.
12. Если API или техническая возможность неизвестна — сначала проверить документацию и только после этого реализовывать интеграцию.

## Итоговая архитектурная идея

Основная система работает независимо от Maxim: `Instagram → AI → Order Management → PostgreSQL → Admin Panel → Reports / Production / Delivery`.

Maxim — внешняя интеграция: `Delivery Service → Maxim Adapter → Maxim API`, или, если API отсутствует: `Delivery Service → Optimized Delivery List → Operator → Maxim`.
