# 03. Бизнес-правила (реализуются в Python, `app/services/`)

Правила здесь — источник истины для сервисов и тестов. LLM их не исполняет и не может обойти.

## 1. Заказ: жизненный цикл

### 1.1 Статусы
- `NEW` — черновик: собирается ботом или администратором, данные могут быть неполными.
- `WAITING_CONFIRMATION` — все обязательные данные есть, клиенту показана сводка, ждём явного «Да».
- `CONFIRMED` — подтверждён клиентом (бот) или создан/подтверждён сотрудником (админка).
- `PREPARING` → `READY` → (`HANDED_TO_COURIER` только для DELIVERY) → `COMPLETED`.
- `CANCELLED` — отменён.

### 1.2 Разрешённые переходы (`app/services/order_rules.py: ALLOWED_TRANSITIONS`)
| из | в |
|---|---|
| NEW | WAITING_CONFIRMATION, CONFIRMED*, CANCELLED |
| WAITING_CONFIRMATION | CONFIRMED, NEW, CANCELLED |
| CONFIRMED | PREPARING, READY, CANCELLED |
| PREPARING | READY, CONFIRMED, CANCELLED |
| READY | HANDED_TO_COURIER (только DELIVERY), COMPLETED, PREPARING, CANCELLED |
| HANDED_TO_COURIER | COMPLETED, READY, CANCELLED |
| COMPLETED | READY** |
| CANCELLED | — |

`*` NEW→CONFIRMED — только сотрудник (source ADMIN или ручное подтверждение в админке), и только при полноте данных.
`**` COMPLETED→READY — только ADMIN (исправление ошибки); пересчитывает статус клиента.
Любой недопустимый переход → `BusinessRuleError(code="invalid_status_transition")`.
Переход в `WAITING_CONFIRMATION` и `CONFIRMED` требует полноты данных (§1.3), иначе `BusinessRuleError(code="order_incomplete", missing=[...])`.
Отметки времени: `confirmed_at` при входе в CONFIRMED (первый раз), `completed_at` при COMPLETED, `cancelled_at` при CANCELLED.

### 1.3 Обязательные данные (`OrderValidator.missing_fields(order) -> list[str]`)
Порядок списка = порядок уточняющих вопросов бота:
1. `items` — ≥1 позиция, у каждой активный существующий товар и `quantity ≥ 1`;
2. `delivery_date` — не в прошлом (бизнес-таймзона);
3. `delivery_time`;
4. `delivery_type`;
5. `customer_name` — имя клиента (для DELIVERY достаточно `recipient_name`);
6. `phone` — телефон клиента или получателя;
7. только DELIVERY: `address` (есть `address_raw`), `recipient_name`, `location` — координаты **пока адрес не искали** (`geocode_status = PENDING`). После попытки геокодирования (`OK`/`MANUAL` — координаты есть; `NOT_FOUND`/`AMBIGUOUS`/`FAILED` — ссылка на карту предложена, доставка видна оператору без координат, в маршруте — по примерной точке найденного места или `unlocated`, §7) заказ идёт дальше: OSM редко знает номера домов в микрорайонах Худжанда, и клиент этим не блокируется (решение 16.09.2026 по живым диалогам).

`courier_comment`, `comment`, `payment_method` — необязательны (бот может спросить один раз, но не блокирует заказ).

Проверки времени (не блокируют ручное создание администратором, но блокируют бота):
- дата и время не раньше `now + min_lead_time_hours` (настройка, по умолчанию 24) → бот сообщает минимальный срок и самое раннее время (`delivery_too_soon`) и просит другое время. 22.09.2026, решение заказчика: **никаких исключений, заказ берём строго за день** — у «Синнамонов» значение 24, бот не предлагает «спросите, вдруг успеем» (ответ FAQ «Можно ли заказать на сегодня?» отказывает прямо), а `ResponseGuard.same_day_promise` (05 §6) не пропускает обещание «сегодня», пока `min_lead_time_hours > 0`;
- дата не дальше `max_days_ahead` (по умолчанию 60);
- время внутри часов выдачи `order_hours_start`–`order_hours_end` (настройки `HH:MM`, по умолчанию `null` = без ограничения; 18.09.2026: «завтра в 23:30» принималось при работе 9:00–20:00) → `delivery_out_of_hours`: день остаётся, бот называет часы и переспрашивает только время. `working_hours` — только текст для клиентов, по нему ничего не проверяется. Самое раннее время тоже учитывает часы: если `now + min_lead_time_hours` позже закрытия, предлагается открытие следующего дня; без известного времени день проверяется по `order_hours_end` (иначе 23:59).
- дата не приходится на выходной день пекарни — `closed_weekdays` (настройка, список `date.weekday()`: 0 — понедельник … 6 — воскресенье; по умолчанию `[]` = работаем всегда; 21.09.2026 по архиву Instagram: «завтра мы не работаем, в понедельник потом снова будем») → `delivery_closed_day`: сообщается **первым** среди проблем времени, день и время из черновика сбрасываются, бот называет день недели и ближайший рабочий день (`next_open_date`). Самое раннее время тоже перескакивает выходные: если слот попал на выходной, предлагается открытие ближайшего рабочего дня. Все семь дней выходными сделать нельзя (иначе предлагать нечего).
- Согласие на предложенное время (18.09.2026). Предложенный слот хранится в `Conversation.state.offered_slot` ровно до следующего сообщения клиента. «Да» (`classify_confirmation = YES`) или короткое согласие («давайте», «ок», «хорошо», «хоп», «майлаш», «мешад»…) без другого текста записывает этот слот в черновик без LLM, если время ещё не задано и слот по-прежнему допустим. «Да, в 19:00» читает модель как обычно.

Проверка количества (21.09.2026, тоже только для бота — администратор вводит вручную что угодно). Выпечка пакуется коробочками, и пекарня продаёт «либо 4, либо 8»: сумма количеств по всем позициям заказа должна быть не меньше `min_order_quantity` и кратна `order_quantity_step` (обе настройки по умолчанию `1` = правило выключено).
- `quantity_below_min` — заказано меньше минимума; `quantity_not_multiple` — не кратно коробочке.
- Бот не показывает сводку и не подтверждает такой заказ: он называет правило и предлагает **два** допустимых количества — ближайшее меньшее (`quantity_lower`, если оно не меньше минимума) и ближайшее большее (`quantity_upper`): «Сейчас 5 — сделаем 4 или 8?».
- Пока уточняются сами позиции (`pending_items`), количество не проверяется — один вопрос за раз.
- Правило считает штуки по всем позициям, поэтому оно рассчитано на каталог с ценой за штуку. Если товары в каталоге — готовые коробки, кратность ставится в `1`.
- 22.09.2026, решение заказчика: **строго от 4 штук**, ни «одна штука», ни «одна на пробу» исключением не являются (ответы FAQ говорят то же самое). 23.09.2026 добавились **коробочки по 6**: из коробок по 4 и по 6 складывается любое чётное количество от 4, то есть `min_order_quantity = 4`, `order_quantity_step = 2`. Шаг при этом перестал быть размером коробки, поэтому тексты бота называют не «коробочку по N», а сами подходящие количества («подходят 4, 6, 8, 10 и так далее», факт `quantity_examples` / `packing_examples`, `allowed_quantity_examples`). Сколько штук в коробке — в ответах FAQ, которые владелец правит сам.

Коробка и микс вместо вкуса (23.09.2026, живой диалог #3). Клиент часто описывает не вкус, а саму коробку: «обычная стандартная коробка из 6 шт», «можно микс со всеми вкусами». Такие слова (`DESCRIPTOR_STEMS` в `product_matcher.py`) не товар и **никогда** не получают ответ «такого нет в каталоге» — бот спрашивает, какие вкусы. «Микс», «ассорти», «все вкусы», «разные вкусы» (`is_mix_mention`) бот собирает сам: если общее количество известно — из этого же сообщения или из незакрытого вопроса «какие именно?» — и делится на число вкусов, в черновик пишется поровну каждого **стандартного** вкуса (большие размеры в микс не идут, их просят по названию). Если количества нет вовсе, бот спрашивает именно его («Микс соберём из любых вкусов: … Сколько штук нужно?», `pending_items[].mix`) — спросить здесь «какие именно?» значит отправить клиента по второму кругу тем же вопросом, а второй одинаковый ответ подряд уводит диалог оператору (§6). Если количество есть, но не делится на число вкусов (4 штуки на 6 вкусов), бот спрашивает, какие вкусы взять: разложить 4 на 6 — выбор клиента, а не бота.

### 1.4 Суммы (`OrderPricing`)
- Каталог «Синнамонов» — **цена за штуку**, и с прайс-листа от 23.09.2026 у каждого вкуса **два размера**, у каждого своя цена: стандартный (10 / 18 / 23) и большой (15 / 26 / 34). Большой — отдельный товар («Классический большой»), потому что цена отдельная; голое название вкуса по-прежнему означает стандартный — так пишут клиенты в архиве. В названии большого нет слова «синнамон» намеренно: на «хочу 5 синнамонов» бот предлагает шесть вкусов, а не двенадцать строк (`ProductMatcher`, категорийное слово).
- **Каталог группируется по вкусам** (`app/ai/catalog.py: flavour_groups`, 23.09.2026). В БД связи между размерами нет, поэтому пара читается по названию: товары, чьё имя начинается с одного слова, — один вкус, а тот, у кого остаток имени — размерное слово (`SIZE_WORDS`: «большой», «большая», «большие», «калон»), — его большой размер; первый без размера — стандартный. Прайс-лист бот печатает по строке на вкус с обеими ценами («Классический синнамон — 10 сомони / шт, большой — 15 сомони») и одной строкой поясняет размеры («Первая цена — стандартный размер, вторая — большой»; по-таджикски размер называется «калон»). Описания в общем списке не печатаются — они остаются в ответе про конкретный товар. Причина: в живом диалоге #3 на вопрос про товары уходило двенадцать строк с описанием каждая, и заказчик попросил «чтоб не было большого текста». В перечислениях «какие именно?» и «сейчас можно заказать» размеры тоже сворачиваются во вкус, а вот вопрос «какой именно товар вы имели в виду?» (`pending_ambiguous`) показывает их как есть — это и есть его вопрос. Каталог без размеров выводится как раньше.
- При добавлении позиции цена берётся **из БД** (`Product.price`) и сохраняется в `OrderItem.unit_price`; `product_name` — снимок.
- `total_price = quantity × unit_price` (Decimal, ROUND_HALF_UP, 2 знака); `Order.total_amount = Σ total_price`.
- Цена позиции в существующем заказе **не меняется** при изменении цены товара. При замене набора позиций администратором новые позиции берут текущую цену; позиции с тем же `product_id`, что были, сохраняют свою `unit_price`, если `keep_prices=true` (по умолчанию).
- Сумму никогда не принимаем от клиента/LLM. В API создания/изменения заказа поля `unit_price`, `total_price`, `total_amount` не принимаются.
- Режимы изменения набора позиций (`OrderPricing.apply`): `add` — добавить (та же позиция с тем же комментарием суммируется), `replace` — заменить набор, `remove` — убрать (частично или целиком), `set` (17.09.2026, для бота: «шоколадных не 2, а 3») — названные товары получают ровно указанное количество, их `unit_price` сохраняется, `0` удаляет позицию, остальные позиции не меняются.

### 1.5 Изменения и журнал
- Каждое изменение заказа (сервисом, ботом, сотрудником) пишет `OrderEvent` с diff `changes`, `actor_type`, `actor_user_id`.
- События логируются: `order.created`, `order.updated`, `order.status_changed`, `order.payment_changed`, `order.confirmed`, `order.cancelled`.
- Изменение через бота:
  - заказ в `NEW`/`WAITING_CONFIRMATION` → изменения применяются, статус → `NEW` (если стал неполным) или снова `WAITING_CONFIRMATION` с новой сводкой (подтверждение нужно заново);
  - заказ `CONFIRMED` и позже → бот **не меняет** заказ сам: создаёт `OrderEvent(event_type="UPDATED", comment="Клиент просит изменить: ...")`, переводит диалог в `HUMAN_HANDOFF` (needs_attention) и отвечает, что менеджер уточнит.
- Отмена через бота: `NEW`/`WAITING_CONFIRMATION`/`CONFIRMED` — после явного подтверждения отмены (тот же классификатор «да», §5); `PREPARING` и позже — только оператор (handoff).
- **Отказ до оформления** (21.09.2026, диалог №46): черновик создаётся, как только назван вкус, поэтому у клиента заказа ещё нет — он не видел ни сводки, ни номера. Пока черновик «невидимый» (`status=NEW` и `state.summary_hash` пуст), «тогда не надо» **не превращается в отмену**: подтверждения не спрашиваем и номер не называем — черновик тихо отменяется (`cancel_reason` «Клиент отказался до оформления заказа»), ответ шаблоном `DRAFT_DISCARDED` («Хорошо, ничего не записываем…»). Как только сводка показана или заказ подтверждён, работает обычная отмена с подтверждением.
- Брошенный черновик (17.09.2026): черновик, который не менялся 48 ч (`DialogService.DRAFT_ABANDON_HOURS`), при новых позициях от клиента отменяется системой (`actor_type=SYSTEM`, `cancel_reason` «Черновик не завершён клиентом — начат новый заказ») и заказ начинается заново; без новых позиций старый черновик продолжается (05 §5.7.1).

## 2. Клиенты: новый / постоянный
- Клиент **постоянный** (`is_new=false`), если у него есть хотя бы один заказ в статусе `COMPLETED`. Иначе **новый** (`is_new=true`). (SPEC §16: «Новый — без завершённых предыдущих заказов».)
- `CustomerService.recalculate_status(customer_id)` вызывается при каждом входе/выходе заказа из `COMPLETED`.
- `Order.is_repeat_customer` — снимок `not customer.is_new` в момент перехода в `CONFIRMED` (первый раз). По нему статистика разделяет заказы новых и постоянных клиентов.
- `Customer.last_order_at` = максимум `confirmed_at` его заказов, кроме `CANCELLED`; пересчитывается при подтверждении/отмене.
- Клиент из Instagram создаётся при первом входящем сообщении (`get_or_create_by_instagram_id`), профиль (name, username) подтягивается из Graph API, если доступен; при ошибке — клиент создаётся без имени.
- Телефон нормализуется и **проверяется** (`app/services/phone.py`, библиотека `phonenumbers`/libphonenumber): номер с `+` или `00` — международный и должен быть валиден для своей страны; без `+` — таджикский: `9 цифр` (`92 780 91 52`), `992` + 9 цифр, префикс `8`/`0` + 9 цифр; 11 цифр с `7`/`8` — российский без плюса. Всё, что libphonenumber отвергает (лишняя цифра — `9277373738292`, `9277777777`, несуществующий код оператора), → не сохраняем, бот переспрашивает и называет два формата: `92 780 91 52` или `+992 92 780 91 52`. Результат — E.164.
- **Чёрный список** (`Customer.is_blocked`, решение 17.09.2026 по запросу заказчика): сотрудник вручную ставит флаг в карточке клиента (`PATCH /customers/{id} {is_blocked}`) — критерии (затягивает диалог, торгуется, отказывается от предоплаты и т.п.) намеренно не автоматизированы через AI, чтобы не забанить случайно обычного осторожного клиента. Пока флаг стоит, `DialogService` проверяет его **до** любого обращения к LLM (даже раньше проверки на явную просьбу оператора): на первое сообщение бот отвечает фиксированным шаблоном `BLOCKED` («К сожалению, в данное время мы не можем принять Ваш заказ.») и ставит `needs_attention=true`; на все следующие сообщения того же диалога — не отвечает вообще (`DialogState.blocked_notice_sent` в JSON-состоянии диалога помнит, что отказ уже отправлен). Разблокировка — тем же PATCH.

## 3. Оплата
- **Оплата временно выключена** (22.09.2026, решение заказчика: «оплату пока отключить; как только бот будет готов ко всем ситуациям — подключим, наработки не убирать»). Код предоплаты и чеков остаётся целиком; выключает её одна настройка `prepayment_enabled=false` («Настройки → Предоплата»), и вместе с ней выключается всё, что о ней говорит:
  - ответы FAQ про предоплату (`scripts/faq_data.py: PREPAYMENT_QUESTIONS` — «Нужна ли предоплата?», «Можно ли заплатить при получении?», «Можно ли оплатить картой или переводом?», «Доставку тоже переводом оплачивать?») переводятся в `is_active=false` и возвращаются вместе с переключателем (`scripts/seed_demo.py: seed_faq`);
  - `payment_methods_text` в настройках очищается (`seed_settings` меняет его, только пока там стоит один из текстов набора, — правку владельца в панели не трогает);
  - в итоге вопрос об оплате не получает выдуманного ответа: нет ни политики, ни номера, поэтому бот отвечает «Мне нужно уточнить эту информацию у менеджера» и помечает диалог `needs_attention`.
- Ручная смена `payment_status` сотрудником и регистрация платежей используют один сервис `PaymentService`, чтобы `paid_amount`, `payments` и `payment_status` всегда были согласованы:
  - `POST /orders/{id}/payments {kind, amount, method}` → запись Payment → пересчёт.
  - `PATCH payment_status=PAID` → создаётся Payment(PAYMENT) на `total − paid` (если > 0).
  - `PATCH payment_status=UNPAID` → создаётся корректирующая Payment(REFUND) на `paid` (если > 0) с `note="Ручная корректировка"`; разрешено ADMIN и OPERATOR, пишется событие.
  - `PATCH payment_status=PARTIALLY_PAID` требует `paid_amount` (0 < x < total) → Payment на разницу (PAYMENT или REFUND).
  - `PATCH payment_status=REFUNDED` → Payment(REFUND) на весь `paid`, статус фиксируется как REFUNDED.
- Пересчёт: `paid = Σ PAYMENT − Σ REFUND`. Статус: был возврат и `paid == 0` → `REFUNDED`; `paid == 0` → `UNPAID`; `0 < paid < total` → `PARTIALLY_PAID`; `paid ≥ total` (и total > 0) → `PAID`.
- Если после изменения позиций `total` изменился — статус оплаты пересчитывается.
- Все изменения оплаты → `OrderEvent(PAYMENT_CHANGED)` и лог `order.payment_changed`.
- **Предоплата и чек** (17.09.2026, решение заказчика «пока временно просим предоплату на кошелёк»). Настройки `prepayment_enabled`, `prepayment_percent` (доля суммы, по умолчанию 100), `prepayment_wallet` (**номер счёта владельца: кошелёк-телефон в Душанбе Сити / Алиф / Эсхата или номер карты** — 13 цифр и больше считается картой, `is_card_number`, и тексты говорят «карта/карту», иначе «кошелёк»), `prepayment_wallet_banks`, `prepayment_auto_confirm` (04 §12). Пока политика включена:
  - после «Да» клиента к шаблону подтверждения добавляется просьба: «Предоплата — {сумма}: переведите на кошелёк/карту {wallet} ({banks}) и пришлите чек — скриншот перевода»; сумма = `percent%` от `total_amount` минус `paid_amount`; тот же номер называется в ответе на вопрос об оплате;
  - **чек** — изображение от клиента, у которого есть оформленный неоплаченный заказ (`CONFIRMED…HANDED_TO_COURIER`, `payment_status` UNPAID/PARTIALLY_PAID, сумма > 0): бот читает скриншот моделью (`app/ai/receipt.py`, 05 §9) и **детерминированно** сверяет: статус перевода (успешен), валюту (сомони), получателя с нашим номером (маскированные цифры «+992 92 *** 53 33», «5058 27** **** 6297» — подстановочные; карта/счёт, когда у нас кошелёк-телефон, — не совпадение; только имя — сравнить нельзя, не блокирует), сумму (не меньше ожидаемой предоплаты; ожидаемая = доля от суммы заказа минус большее из «зарегистрированные платежи» и «суммы прежних чеков этого заказа без проблем, кроме нехватки» — поэтому «переведите ещё 250» и чек на 250 сходятся). Результат записывается в журнал заказа (`OrderEvent(UPDATED)`, «Чек из Instagram: 300.00 сомони, Alif, получатель совпадает, … Сверьте поступление в приложении банка»), диалог помечается `needs_attention`, клиенту — шаблон `RECEIPT_RESULT`: «чек получили, менеджер сверит» / «не хватает N сомони» / «перевод нужен на наш кошелёк/карту» / «перевод не прошёл» / «сумму не разобрать»;
  - **подлинность** (18.09.2026, вопрос заказчика «проверять чек на фотошоп и ИИ-генерацию»). Доказать подделку по скриншоту нельзя (Instagram пересжимает картинку и срезает метаданные), поэтому проверяется то, что проверяемо; каждый распознанный чек сохраняется в `payment_receipts` (02):
    - **повтор** — тот же файл (SHA-256), тот же номер операции или тот же перевод (сумма + минута + отправитель) уже присылали: к **другому** заказу → проблема `duplicate`, клиенту «этот чек уже присылали к другому заказу, пришлите чек по новому переводу», оператору «ВНИМАНИЕ: этот чек уже присылали к заказу №N (тот же файл / номер операции / перевод)»; к **этому же** заказу → `resent`, клиенту «этот чек мы уже получили», в сумму второй раз не засчитывается;
    - **дата** (модель переписывает её в ISO, сравнивает Python в часовом поясе бизнеса): перевод в будущем (позже «сейчас» + 15 мин) → тревога `date_future`; перевод раньше создания заказа больше чем на час → `date_before_order`; дата без времени считается целым днём;
    - **следы правки** — отдельный узкий вызов модели `inspect_receipt` (05 §9): одно значение другим шрифтом, цветом или на заплатке другого фона → тревога `looks_edited` с указанием строки;
    - **тревоги (`date_*`, `looks_edited`) клиенту не показываются**: он получает обычное «чек получили, менеджер сверит» — ложное обвинение хуже подделки, которую сотрудник всё равно увидит в приложении банка. Тревога или проблема делает `ok=false`, поэтому автоотметка оплаты при сомнении не срабатывает никогда; в журнале заказа — «ВНИМАНИЕ: …»;
  - **бот сам оплату не отмечает**: скриншот можно подделать, поступление подтверждает только приложение банка, поэтому оплату ставит сотрудник (ADMIN/OPERATOR, как и раньше). Исключение — `prepayment_auto_confirm=true` (осознанное решение владельца, по умолчанию выключено): при полном совпадении суммы и получателя и без единой тревоги бот регистрирует `Payment(PAYMENT, TRANSFER, «По чеку из Instagram (отмечено ботом автоматически)»)` от `actor_type=AI`, заказ становится оплаченным, оператор всё равно видит `needs_attention` для сверки;
  - картинка, которая не чек (модель: `is_receipt=false` или низкая уверенность), модель недоступна, политика выключена, заказа нет или он оплачен → изображение уходит оператору, как раньше (§6);
  - «оплатил» / «перевёл» / «пардохт кардам» текстом при ожидаемой предоплате → шаблон `ASK_RECEIPT` «пришлите чек» без модели.

## 4. Статистика, производство, отчёт
- **Учитываемые заказы** («valid»): статусы `CONFIRMED, PREPARING, READY, HANDED_TO_COURIER, COMPLETED`. `NEW`, `WAITING_CONFIRMATION`, `CANCELLED` не учитываются нигде в выручке/производстве.
- **База даты** периода: по умолчанию `delivery_date` (день выдачи/доставки); параметр `date_basis=created` — по дате подтверждения (`confirmed_at` в бизнес-таймзоне).
- Периоды: `today`, `yesterday`, `week` (последние 7 дней включая сегодня), `month` (с 1-го числа текущего месяца по сегодня), `custom` (`date_from`..`date_to` включительно).
- **Финансы**: `revenue = Σ total_amount`; `orders_count`; `paid_orders_count` (`PAID`); `partially_paid_orders_count`; `unpaid_orders_count` (`UNPAID`); `paid_amount = Σ min(paid_amount, total_amount)`; `unpaid_amount = revenue − paid_amount`; `average_check = revenue / orders_count` (0 при 0 заказов).
- **Клиенты**: `new_customers` — число различных клиентов с valid-заказами периода, где `is_repeat_customer=false`; `regular_customers` — где `true` (клиент считается в той группе, к которой относится его первый заказ периода); `new_customer_orders`, `regular_customer_orders`; `total_customers` — всего клиентов в БД; `customers_registered` — созданы в периоде.
- **Доставка**: `delivery_orders`, `pickup_orders` среди valid.
- **Расходы и прибыль** (17.09.2026, запрос заказчика сверх SPEC §20): сотрудник вносит расходы вручную (`expenses`: дата, категория, сумма > 0, комментарий; дата не в будущем; добавлять/менять/удалять — ADMIN, смотреть — STAFF). Для периода: `expenses = Σ amount` расходов с `expense_date` в периоде — **всегда по дате расхода**, независимо от `date_basis`; `profit = revenue − expenses` (может быть отрицательной); `margin_percent = profit / revenue × 100`, округление ROUND_HALF_UP до 0,1, `null` при `revenue = 0`; `expenses_by_category` — только ненулевые категории, по убыванию суммы (при равенстве — порядок enum). В ежедневный отчёт (SPEC §22, строгий формат) расходы не входят.
- **Производственная сводка на дату D**: valid-заказы с `delivery_date = D`; группировка позиций по `product_id` (если null — по `product_name`), сумма `quantity`; сортировка по `Product.sort_order`, затем имени. Текст:
  ```
  Заказы на 16 сентября:

  Красный бархат — 5 шт.
  Медовик — 4 шт.
  ```
- **Ежедневный отчёт за D** (`ReportService.build_daily(D)`): финансы + клиенты + доставка + производство на D, `date_basis=delivery`. Текст строго в формате SPEC §22; суммы форматируются `12 500 сомони` (разделитель тысяч — пробел; копейки только если не ноль: `12 500,50 сомони`). Генерируется задачей Celery beat ежедневно в `daily_report_time` (настройка, по умолчанию `21:00` бизнес-времени) и сохраняется/перезаписывается в `daily_reports`.

## 5. Подтверждение заказа (защита от ошибочного подтверждения)
`app/ai/confirmation.py: classify_confirmation(text: str) -> ConfirmationDecision` — **детерминированный** классификатор, LLM не может подтвердить заказ.
- Нормализация: lower, `ё→е`, убрать эмодзи и пунктуацию, схлопнуть пробелы.
- `YES` только если: сообщение короткое (≤ 6 слов), содержит явную фразу согласия и **не** содержит маркеров сомнения, отрицания или изменений.
  - RU согласие: `да`, `подтверждаю`, `все верно`, `верно`, `да верно`, `да все верно`, `да подтверждаю`, `все правильно`, `правильно`, `согласен`, `согласна`.
  - TG согласие: `ҳа`, `ха`, `бале`, `тасдиқ мекунам`, `тасдик мекунам`, `дуруст`, `дуруст аст`, `ҳама дуруст`, `хама дуруст`, `ҳамааш дуруст`; худжандское `рост` («верно»): `рост`, `ҳа рост`, `ҳамааш рост` (18.09.2026).
- `UNCERTAIN` при маркерах сомнения: `наверное`, `вроде`, `может`, `может быть`, `посмотрим`, `думаю`, `кажется`, `скорее всего`, `не знаю`, `не уверен`, `не уверена`, `ну`, `наверно`, `шояд`, `эҳтимол`, `балки`, `мумкин`, `мебинем`, `фикр мекунам`, `фикр мекнам`, `намедонам`; при одиночных эмодзи/стикерах и слабых «ок» (`👍`, `✅`, `ок`, `ok`, `ага`, `угу`, `хуб`, `майлаш`, худжандские `боша`, `нағз`, `майли`) — бот просит написать «Да».
- `NO` при отрицании/изменении: `нет`, `не`, `неверно`, `не так`, `отмена`, `отменить`, `измените`, `поменяйте`, `не надо`, `не`, `нест`, `хато`, `хато аст`, `не дуруст`, `ин хел не`, `бекор`.
- `CHANGE` — если после согласия есть содержательные детали («да, но время 19:00») → изменения применяются, сводка показывается заново.
- Переход `WAITING_CONFIRMATION → CONFIRMED` выполняется **только** при `YES` **и** если с момента показа сводки заказ не менялся (`state.summary_version == order.version_hash`). Иначе — повторный запрос подтверждения.
- Обязательные тест-кейсы: «Да», «Подтверждаю», «Всё верно» → YES; «ну вроде», «наверное», «может быть», «посмотрим», «думаю да» → UNCERTAIN (не подтверждать).

## 6. Передача оператору (HUMAN_HANDOFF)
- Причины: явная просьба (`OPERATOR_REQUEST` от LLM **или** детерминированные ключевые слова: `оператор`, `человек`, `менеджер`, `администратор`, `живой`, `позовите`, `оператор лозим`, `одам`, `менеҷер`); `COMPLAINT`; 2 подряд неудачные попытки понять (`failed_ai_attempts ≥ 2`); ошибка/недоступность LLM; изменение/отмена заказа в производстве; изображение с запросом индивидуального дизайна (решение оператора) — кроме чека об оплате при ожидаемой предоплате (§3: бот читает его сам и остаётся в диалоге).
- **Косяк с нашей стороны** (22.09.2026, решение заказчика «если с нашей стороны происходит какой-то косяк — сразу передаём менеджеру», `reason_code=complaint`, причина «Клиент пишет о проблеме с нашей стороны»). Детерминированный детектор `app/ai/handoff.py: detect_our_fault` работает на шаге 2 (05 §5), до модели и до FAQ: «не привезли», «так и не ответили», «перепутали», «не хватает», «черствые», «верните деньги», «буду жаловаться», худжандские «дер кардед», «нарасид», «наовардед», «хунук буд». Бот не объясняется и не отвечает из FAQ — «Извините за неудобства. Передаю диалог менеджеру». Детектор смотрит только на **уже случившееся**: вопрос о будущем («а если не привезёте вовремя?») и возражения, на которые есть ответ в FAQ («почему так дорого?», «надеюсь, не обманете»), остаются боту.
- **Дословный повтор** (21.09.2026, `reason_code=repeated_reply`): если ответ на сообщение клиента слово в слово совпал бы с предыдущей репликой бота (пробелы и регистр не считаются различием), он не отправляется — диалог передаётся менеджеру. Клиент переспросил, а бот ответил бы тем же абзацем: добавить ему нечего. Правило не касается продолжений, которые начал не клиент (метка на карте, чек): повторная сводка заказа — не повтор.
- Действие: `conversation.mode = HUMAN_HANDOFF`, `handoff_reason`, `handoff_at`, `needs_attention = true`; клиенту — одно сообщение «Передаю диалог менеджеру, он скоро ответит» (на языке клиента).
- В режиме `HUMAN_HANDOFF` входящие сохраняются (STT для голосовых выполняется), но **бот не отвечает**.
- Сотрудник отвечает из «Диалогов»; кнопка «Вернуть боту» → `mode = AI`, `needs_attention = false`, `failed_ai_attempts = 0`.

## 6a. Догоняющие вопросы (бот пишет первым)
Решение заказчика 22.09.2026. В архиве Instagram это самая постоянная привычка владельца: клиент сказал «даа», обещал чек — и пропал, а через несколько часов приходит «Вам коробку оставить или нет», «Заказ кабул кунам е не», «Мне для оформления заказа чек нужен или вы передумали?» (41 случай) — и заказ спасён. Бот раньше только отвечал; теперь у него есть эта привычка (`app/services/follow_up_service.py`, задача `send_follow_ups` каждые 15 минут, 06 §5).

- **Когда**: бот ждёт клиента, а не наоборот. Три стадии, по одному вопросу на каждую:
  - `draft` — черновик собирается, вопрос бота остался без ответа → «Вам коробочку оставить? …» плюс тот самый вопрос (первое из `missing_fields`);
  - `confirmation` — сводка показана, «Да» не пришло → «Подскажите, заказ оформляем?..». Номер заказа не называется: у клиента заказа ещё нет (05 §6);
  - `receipt` — заказ оформлен и ждёт предоплаты (только когда «Предоплата» включена) → «Мне для оформления заказа чек нужен, или вы передумали?».
- **Задержка**: `follow_up_after_hours` (настройка, по умолчанию 3 ч тишины), выключатель — `follow_up_enabled` (04 §12). Считается от последнего сообщения в диалоге.
- **Когда бот молчит**: диалог у менеджера (`HUMAN_HANDOFF`) или помечен `needs_attention`; последнее сообщение — от клиента (тогда бот должен ответить, а не напоминать); клиент в чёрном списке; `ai_enabled=false`; об этой стадии этого заказа уже напоминали (`state.follow_ups_sent`, 05 §4); вне часов выдачи (`order_hours_*`, иначе 9:00–21:00) — сообщение, которое начинаем мы, ждёт рабочего времени; **окно Instagram закрыто** (06 §1) — после 24 часов отправить нечего, поэтому такие диалоги даже не рассматриваются.
- Текст — всегда шаблон (`ReplyKind.FOLLOW_UP`, 05 §6): отвечать не на что, модели нечего формулировать.
- Тому, кто просто спросил и ушёл, ничего не приходит: без начатого заказа стадии нет. Рассылок и «а не хотите ли ещё» бот не делает.

## 7. Доставка, геокодирование, маршрут
- `Delivery` создаётся/обновляется, когда у заказа `delivery_type = DELIVERY` и получен адрес; при смене на PICKUP — удаляется (если нет dispatch).
- Источники координат по приоритету достоверности: `CUSTOMER_PIN` (клиент отметил точку по ссылке) = `OPERATOR` (сотрудник поставил точку) > `GEOCODER`.
- Геокодирование (`GeocodingService`): провайдер по настройке. Автопринятие (`geocode_status=OK`) только если ровно 1 кандидат высокой точности (дом/здание) и точка внутри bbox города. Иначе:
  - текст клиента разбирается на части (`app/integrations/maps/address.py`: район, номер микрорайона, улица с нормализованным типом, дом — в т. ч. «5 дом», квартира/подъезд/этаж — только для курьера, ориентир — после «возле/рядом с/ориентир» или по слову-типу без предлога: «Панчшанбе бозор», «магазин Анвар»; кӯча → улица, хиёбон → проспект) и геокодируется **лестницей** запросов (не более 4): дом (улица + дом или «N мкр, дом»; для «10/2», «12а» затем основной номер «10», «12» — дробей в OSM почти нет); ориентир в форме OSM («возле рынка Панчшанбе» → «рынок Панчшанбе», «Панчшанбе»; «26 школы» → «школа 26»); улица; «N микрорайон» → «N мкр»; сырой текст; названный район. Новый адрес от клиента сбрасывает разобранные части прежнего адреса (иначе геокодировался бы старый микрорайон/дом). **Первый найденный дом побеждает**; до того запоминается лучшее приблизительное попадание: ориентир > улица > микрорайон/район > прочее, а запросы центра улицы/микрорайона пропускаются, если это место уже известно. Результат ориентира никогда не принимается автоматически (точность понижается до `other`, только внутри bbox города): клиент рядом с ним, а не в нём. Кандидаты, противоречащие запросу (другой номер микрорайона, другая улица), отбрасываются; POI на доме сворачивается в дом; один и тот же адрес («115, улица Гагарина», подъезды «1-2 подъезд, 29, …») в пределах 300 м — один кандидат, а не выбор. Ошибка провайдера посреди лестницы не отменяет уже найденное место. Проверено живьём на 20 типичных адресах Худжанда (18.09.2026): до дома 5 → 7, «не найдено» 9 → 4;
  - 0 кандидатов → `NOT_FOUND`: бот просит уточнить адрес (район, микрорайон/улица, дом, ориентир) и присылает ссылку «Отметьте точку на карте»;
  - >1 кандидата дома → `AMBIGUOUS`, `geocode_candidates` сохраняются: бот перечисляет до 3 вариантов (только точность «дом») и ссылку на карту; найдена только улица/микрорайон → `AMBIGUOUS` с одним приблизительным кандидатом: бот пишет «нашли улицу, но не дом», ссылка на карту центрируется на нём (`suggested` в `GET /public/location`);
  - ошибка/не настроен провайдер → `FAILED`: бот пишет, что адрес проверить не удалось и курьер уточнит по телефону, ссылка на карту всё равно предлагается, заказ помечается для проверки оператором (`needs_attention`).
  - Во всех трёх случаях заказ **не блокируется** (§1.3 п. 7): следующие вопросы задаются сразу, а полный заказ клиент продолжает словом «дальше»/«ок» (детерминированный `small_talk` ACK) или точкой на карте (`continue_dialog_after_location`).
- **Доставка платная всегда** (22.09.2026, решение заказчика: «для первого раза никакой бесплатной доставки»). В архиве Instagram владелец иногда отвечал «вам на первый раз да)» — бот так не делает: бесплатен только самовывоз. Правило живёт в текстах для клиента (`delivery_info_text` в настройках и ответ FAQ «Первая доставка бесплатная?»), стоимость доставки в сумму заказа не входит и остаётся за таксистом.
- Ссылка на карту: `LocationRequest` (TTL 48 ч), публичная страница фронтенда `/l/{token}`; сохранение точки → `latitude/longitude`, `location_source=CUSTOMER_PIN`, `geocode_status=MANUAL`, копирование в `orders.delivery_*`, повторная проверка полноты заказа и продолжение диалога (бот отправляет сводку).
- **Оптимизация маршрута** на дату D (`RouteOptimizationService`): доставки valid-заказов с `delivery_type=DELIVERY`, `delivery_date=D`; старт — склад/кухня из настроек (`warehouse`). Точка остановки (`stop_point`): координаты доставки; иначе при `AMBIGUOUS` — первый сохранённый кандидат внутри bbox города (микрорайон, улица, ориентир), остановка помечается `approximate` с названием места («28 микрорайон, г.Худжанд»), курьер звонит клиенту (18.09.2026: OSM редко знает номера домов Худжанда, и без этого маршруты тестовых дней были пустыми). Доставки без какой-либо точки (`NOT_FOUND`, `FAILED`, `PENDING`) перечисляются отдельно как `unlocated`; остановка сохранённого плана, чья доставка потеряла точку (клиент сменил адрес), при чтении плана тоже показывается в `unlocated`.
  - Матрица времени/расстояний: провайдер `osrm` (если `OSRM_URL` задан) иначе `haversine` (расстояние по сфере × коэффициент извилистости 1.3, скорость `average_speed_kmh`, по умолчанию 25) — это явная оценка, в ответе `distance_source`.
  - Алгоритм (`app/services/route_optimizer.py`, чистая функция без БД): открытый маршрут от склада; стоимость = время в пути + `lateness_weight` × опоздание сверх окна (`delivery_time ± delivery_time_window_minutes`, по умолчанию ±60); `n ≤ 8` — полный перебор; иначе nearest neighbour + 2-opt + Or-opt до сходимости. ETA = `start_time` + пути + `service_time_minutes` (по умолчанию 5) на каждой точке; ранний приезд — ожидание до начала окна.
  - Результат сохраняется в `RoutePlan`/`RouteStop`; выход: порядок, адрес, координаты (и `approximate`/`approximate_place`), ETA и желаемое время, телефон, получатель, комментарий курьеру. `total_duration_s` — от старта до конца обслуживания последней точки, **включая ожидание** окон доставки; время в пути — сумма `duration_from_prev_s` (так их и показывает админка).
- **Maxim** (`03`→ см. `06-integrations.md`): официального API нет (docs/research/maxim.md, вердикт C) → режим `MAXIM_MANUAL`: «Передать в Maxim» формирует копируемую карточку/список в порядке маршрута; оператор вручную создаёт заказ в приложении Maxim, вносит номер/курьера; статусы доставки меняет вручную.
