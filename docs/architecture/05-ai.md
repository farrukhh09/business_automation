# 05. AI-модуль и обработка диалога

Принцип (SPEC §3, §38–40): LLM **понимает** и **формулирует**, backend **решает** и **исполняет**. Весь код LLM — в `backend/app/ai/`; бизнес-логика диалога — в `backend/app/services/dialog_service.py`.

## 2. LLM-клиент (`llm_client.py`)

```python
class LLMClient(Protocol):
    def complete_json(self, *, system: list[dict], messages: list[dict], schema: dict,
                      tools: list[dict] | None = None, tool_executor: Callable[[str, dict], dict] | None = None,
                      max_tool_rounds: int = 3) -> dict: ...
    def complete_text(self, *, system: list[dict], messages: list[dict], max_tokens: int = 1024) -> str: ...
```

`AnthropicLLMClient` (официальный SDK `anthropic` 1.x):
- `anthropic.Anthropic(api_key=settings.LLM_API_KEY, timeout=settings.LLM_TIMEOUT_SECONDS, max_retries=2)`; модель `settings.LLM_MODEL` (default `claude-opus-5`); `output_config={"effort": settings.LLM_EFFORT}` (default `medium` — чат, чувствителен к задержке; меняется через env).
- Структурированный результат: `output_config.format = {"type": "json_schema", "schema": ...}` (схема со `additionalProperties: false`, все поля в `required`, отсутствие значения — `null`). Tools read-only определяются со `strict: true`; цикл `stop_reason == "tool_use"` → исполнить через `tool_executor` → вернуть **все** `tool_result` одним user-сообщением; максимум `max_tool_rounds`.
- Отказ модели: по умолчанию серверные fallbacks — `client.beta.messages.create(..., betas=["server-side-fallback-2026-07-01"], fallbacks="default")` (настройка `LLM_FALLBACKS_ENABLED=true`). Всегда проверять `stop_reason == "refusal"` до чтения `content` → `LLMRefusalError`.
- Ошибки SDK ловятся цепочкой (`RateLimitError` → `APIStatusError` → `APIConnectionError`) и превращаются в `LLMUnavailableError`.
- Кэширование промптов: стабильная часть системного промпта (правила + описание схемы) — первый блок `system` с `cache_control: {"type": "ephemeral"}`; каталог/FAQ — второй блок (меняется редко); дата/время, состояние диалога и история — только в `messages` (после точки кэша). Никаких `datetime.now()` в `system`.
- Логирование: `ai.request` (модель, intent-этап, число сообщений, без персональных данных сверх id диалога), `ai.response` (stop_reason, usage, структурированный результат), `ai.error`.
- Если `LLM_API_KEY` не задан → `IntegrationNotConfiguredError`; `DialogService` в этом случае делает handoff оператору.

Экономия запросов (16.09.2026, после упора в бесплатные лимиты Gemini): `LLM_TOOLS_ENABLED=false` — понимание без read-tools (каталог и FAQ и так в промпте, без лишних раундов); `LLM_REPLY_WORDING_ENABLED=false` — тексты всех ответов из шаблонов, без второго запроса. По умолчанию обе `true`.

Провайдер выбирается `LLM_PROVIDER` (`anthropic` по умолчанию | `gemini`); `get_llm_client` возвращает нужный адаптер, остальной код от провайдера не зависит.

`GeminiLLMClient` (решение заказчика 16.09.2026 — дешёвая/бесплатная модель для проверки; сверено с ai.google.dev 16.09.2026):
- `POST https://generativelanguage.googleapis.com/v1beta/models/{LLM_MODEL}:generateContent`, ключ в заголовке `x-goog-api-key`; `LLM_MODEL` обязан быть моделью Gemini (например `gemini-3.8-flash`), `claude-*` → `IntegrationNotConfiguredError`.
- Промпты те же (`prompts.py`): блоки `system` → `systemInstruction.parts` (`cache_control` отбрасывается), `messages` → `contents` с ролями `user`/`model`.
- JSON: `generationConfig.responseMimeType="application/json"` + `responseJsonSchema`. Tools → `functionDeclarations[].parametersJsonSchema`; ход модели с `functionCall` возвращается в историю без изменений (thought signatures), результаты — одним `user`-ходом `functionResponse` с `id` вызова; на последнем раунде `functionCallingConfig.mode="NONE"`. JSON + tools поддерживают только модели Gemini 3: при 400 запрос один раз повторяется без tools (каталог и так в промпте).
- `LLM_EFFORT` и `LLM_FALLBACKS_ENABLED` не используются. Для текста `maxOutputTokens ≥ 8192` (размышления модели входят в лимит). Повторы: 5xx/сеть/таймаут — до 3 раз (2, 4, 8 с); 429 ждёт ровно `retryDelay`/`Retry-After` в пределах 75 с на все попытки; исчерпанная **суточная** квота (`quotaId` с `PerDay`; на бесплатном тарифе, напр., 20 запросов в сутки для `gemini-3.6-flash`) не ждётся — сразу handoff. `promptFeedback.blockReason` и `finishReason` из группы безопасности → `LLMRefusalError`.
- **Ограничение:** на бесплатном тарифе Google использует запросы для улучшения своих продуктов, лимиты запросов малы — для реальных клиентов нужен платный ключ или другой провайдер.

## 3. Понимание сообщения (`understanding.py`)

Вход LLM (user-сообщение, собирается `prompts.build_understanding_messages`):
- текущие дата/время/день недели в `Asia/Dushanbe`;
- активный каталог: `[{id, name, aliases, price, unit}]`, FAQ `[{id, question}]` (для выбора `faq_ids`);
- известное о клиенте: имя, телефон, язык, постоянный/новый;
- состояние диалога и текущий черновик заказа (позиции, дата, время, тип, адрес, чего не хватает, ждём ли подтверждения);
- последние 20 сообщений диалога (роль + текст);
- новое сообщение клиента.

Выход — `UnderstandingResult`:

```json
{
  "language": "ru | tg",
  "intent": "FAQ | PRODUCT_QUERY | CREATE_ORDER | CHANGE_ORDER | CANCEL_ORDER | DELIVERY_QUERY | PAYMENT_QUERY | ORDER_STATUS | GREETING | COMPLAINT | OPERATOR_REQUEST | OTHER",
  "secondary_intents": ["..."],
  "entities": {
    "customer_name": null, "phone": null,
    "items": [{"product_id": null, "product_text": "медовик", "quantity": null, "comment": null}],
    "items_mode": "add | replace | remove | set | none",
    "delivery_date": null, "delivery_time": null, "delivery_type": null,
    "address": null, "recipient_name": null, "recipient_phone": null,
    "courier_comment": null, "payment_method": null, "comment": null
  },
  "faq_ids": [],
  "product_ids_asked": [],
  "confirmation_signal": "yes | no | unclear | none",
  "address_candidate_choice": null,
  "confidence": 0.0
}
```

Правила промпта (дублируются проверками backend): не придумывать значения — неизвестное = `null`; `product_id` только из переданного каталога, иначе `null` + `product_text` (латиница «tort», «korobka» → кириллицей «торт», «коробка»: backend сопоставляет только кириллицу); даты — ISO `YYYY-MM-DD`, относительные («завтра», «фардо», «пагоҳ») разрешать от переданной текущей даты; время `HH:MM` 24ч; `quantity` — целое или `null` («2 торта» без названия → `product_text="торт"`, `quantity=2`).

`items_mode` (17.09.2026 добавлен `set`): `add` — клиент называет, что заказать, или добавляет («и ещё 2 шоколадных»); `set` — исправляет количество товара, который уже есть в черновике («шоколадных не 2, а 3», «сделайте 3 шоколадных»): названные товары получают ровно это количество, остальные позиции не трогаются (раньше такая поправка либо удваивала позицию через `add`, либо стирала остальные через `replace`); `replace` — заменяет или пересказывает весь заказ («вместо этого», «я же сказал 3 ягодных и 2 фисташковых»); `remove` — убирает; `none` — позиций нет.

SPEC §10 поля (`product`, `quantity` на верхнем уровне) выводятся из `entities.items` для логов/`ai_payload`.

## 4. Состояние диалога (`Conversation.state`, пишет только backend)

```json
{
  "draft_order_id": 12,
  "awaiting": "missing_fields | confirmation | cancel_confirmation | address_choice | null",
  "missing_fields": ["delivery_time", "delivery_type"],
  "summary_hash": "sha256 содержимого заказа на момент показа сводки",
  "pending_items": [{"kind": "generic | ambiguous | quantity", "product_text": "торт", "quantity": 2,
                     "product_id": null, "name": null, "options": [12, 7], "comment": null}],
  "address_candidates": [{"formatted": "...", "lat": 38.5, "lng": 68.7}],
  "cancel_order_id": 15,
  "language": "ru",
  "last_intent": "CREATE_ORDER",
  "follow_ups_sent": ["draft:12"]
}
```
`pending_items`: `generic` — «2 торта» без названия (варианты — все товары категории), `ambiguous` — текст подходит к нескольким товарам, `quantity` — товар назван без количества. `address_candidates` — не более 3 вариантов внутри Таджикистана. `cancel_order_id` — заказ из вопроса «Отменить заказ №N?» (может быть уже не черновиком). `follow_ups_sent` — стадии, о которых уже напоминали (`"{stage}:{order_id}"`, 03 §6a): клиента не догоняют дважды об одном и том же; хранятся последние 8. Состояние читается терпимо (`DialogState.from_json`): неизвестные ключи и битые значения отбрасываются.

`order_content_hash(order)` = sha256 от канонического JSON (позиции product_id/название/quantity/unit_price/comment, delivery_type/date/time, способ оплаты, комментарий, сумма, имя и телефон клиента, адрес, координаты, получатель, телефон получателя) — всё, что показывает сводка.

## 5. DialogService: алгоритм (детерминированный)

`handle_incoming(conversation, message) -> DialogOutcome{reply_plan, actions_log}`:

1. Если `settings.ai_enabled == false` или `conversation.mode == HUMAN_HANDOFF` → ответа нет (`needs_attention=true` при AI off).
1a. Если `customer.is_blocked` (чёрный список, ставится вручную в админке, 03 §2) → план `BLOCKED` (шаблон, без LLM) один раз (`state.blocked_notice_sent`), дальше — полное молчание; проверяется раньше даже явной просьбы позвать оператора, LLM не вызывается вовсе.
1b. **Чек об оплате** (17.09.2026, 03 §3): изображение при включённой предоплате и оформленном неоплаченном заказе клиента → `read_receipt` (модель читает скриншот в JSON: `is_receipt`, `status`, `amount`, `currency`, `recipient`, `provider`, `paid_at`, `confidence`) → `check_receipt` (Python сверяет статус, валюту, кошелёк, сумму) → строка в журнале заказа + `needs_attention` + план `RECEIPT_RESULT` (шаблон); оплата регистрируется только при `prepayment_auto_confirm`. «Не чек», модель недоступна (handoff «чек распознать не удалось»), политика выключена, заказа нет или он оплачен → изображение уходит оператору, как раньше. Подробнее — §9.
2. `detect_operator_request(text)` (ключевые слова) → handoff (03 §6).
2-. `detect_our_fault(text)` (22.09.2026, 03 §6) → handoff с `reason_code=complaint`: клиент пишет, что мы что-то сделали не так («заказ не привезли», «перепутали вкусы», «дер кардед»). Раньше модели и раньше FAQ, чтобы жалоба не получила ответ по совпавшему ключевому слову; смотрит только на уже случившееся, поэтому «а если не привезёте?» и «почему так дорого?» остаются боту.
2a. **Согласие на предложенное время** (18.09.2026, 03 §1.3): если прошлый ответ назвал самое раннее время (`state.offered_slot`), а клиент ответил «да» / «давайте» / «ок» / «майлаш», слот записывается без LLM. `offered_slot` живёт одно сообщение.
3. Если `state.awaiting == "confirmation"` или `"cancel_confirmation"`: `classify_confirmation(text)`:
   - `YES` + хэш совпадает → `OrderService.confirm(order, actor=CUSTOMER)` → план `ORDER_CONFIRMED` (или `ORDER_CANCELLED`);
   - `NO` → план `ASK_WHAT_TO_CHANGE` (или «заказ не отменён»); `awaiting=null` для cancel;
   - `UNCERTAIN` → повторный запрос подтверждения (`CONFIRMATION_REPEAT`) — **без вызова LLM допустимо**;
   - `CHANGE` → продолжить с шага 4 (извлечь изменения).
3a. **Короткие реплики без LLM** (`app/ai/small_talk.py`, 16.09.2026): сообщение, состоящее только из благодарности («спасибо», «рахмат»), прощания («пока», «хайр») или подтверждения-согласия («ок», «хорошо», «дальше», «хуб») → план `SMALL_TALK` (тёплый ответ + напоминание об открытом заказе), неудачной попыткой не считается. «Ок»/«дальше» при заполняемом черновике = «продолжаем»: следующий вопрос или сводка (так же выходят из запроса точки на карте). **Отказ** (21.09.2026, `SmallTalk.DECLINE`: «тогда не надо», «не буду», «передумал», «даркор нест») распознаётся здесь же и ведёт себя по 03 §1.5: невидимый черновик тихо отменяется, показанный или подтверждённый заказ — через обычное подтверждение отмены, а если открытого заказа нет — вежливый ответ без вопросов. Как и прочие короткие реплики, отказ считается **только по целому сообщению**: «дорого, а скидки есть?» — вопрос, а не отказ; «не надо доставку, сам заберу» — про способ получения. «Подумаю» сознательно не отказ: это «может быть», черновик остаётся. Жалоба на цену — тоже не отказ (22.09.2026, диалог №58): «дорого», «дорого, спасибо», «чаро ин қадар қимат» — это возражение, на которое отвечает запись FAQ «Почему так дорого?» (качественные продукты, выпечка под заказ малыми партиями), а не прощание и не «уточню у менеджера».
   **Приветствие** (17.09.2026, по просьбе заказчика) — сообщение только из приветствия («Добрый день», «Здравствуйте», «Доброе утро», «Добрый вечер», «Салом», «Ассалому алейкум», «Рӯз ба хайр»; допускаются «всем»/«вам» и эмодзи) → план `GREETING` без LLM. Бот отвечает тем же приветствием (`detect_greeting`: `day`/`morning`/`evening`/`salam` → «Ва алейкум ассалом»/`hello` → «Здравствуйте»/«Салом») и спрашивает «Что желаете заказать? 😊»; при открытом черновике вместо этого вопроса — его вопросы или напоминание подтвердить. Приветствие вместе с другим («Здравствуйте, спасибо») считается другой частью; приветствие с вопросом («Добрый день, есть фисташковые?») идёт в понимание как раньше — но и тогда на него отвечают: `DialogService._finish` кладёт в факты любого плана (кроме `GREETING` и `BLOCKED`) `greeting` = найденное приветствие, шаблон начинает ответ с «Добрый день! …»/«Салом! …», а промпт ответа велит модели поздороваться так же (правило 9). Итог: «Здравствуйте, хочу 2 коробки» → «Здравствуйте! Подскажите, пожалуйста, какие именно? …».
   **«Оплатил» / «перевёл» / «пардохт кардам»** (`receipt.mentions_payment_done`, 17.09.2026) при ожидаемой предоплате (03 §3) → план `ASK_RECEIPT` «пришлите чек» без модели; без такого заказа слова идут в понимание как обычно.
4. `understand()` (LLM). Ошибка/отказ LLM → `failed_ai_attempts += 1`, handoff при ≥2, иначе шаблон «Мне нужно уточнить эту информацию у менеджера.» + handoff.
5. `detect_language` (`app/ai/language.py`): буквы `ӣ ӯ ҳ қ ғ ҷ` → tg; иначе счёт слов (сильные/слабые списки RU/TG, таджикская морфология `ме…ам/ем/ед/ид/итон/анд/од`, разговорные формы «мекнам», «мегирм», «ята», латиница «salom, tort mexoham»; названия товаров и деловые заимствования «заказ», «доставка», «самовывоз» — не свидетельство языка); **северные энклитики** (21.09.2026) считаются правилом, а не перечнем написаний: вопрос `-ми` («хастми», «мефурушидми»), притяжательное `-аш` («тайераш»), `-ям` = «тоже» («доставкаям»), местное `-ба`/`-ва` («пагава», «остановкава») — вес 3, если основа известна как таджикская, и 2, если основа русская (русское слово с таджикским окончанием — тоже признак таджикоязычного); `-ми` засчитывается только после таджикской основы, иначе русский творительный падеж («ценами», «разными») читался бы как вопрос; переключение языка только при перевесе ≥ 2 (`SWITCH_MARGIN`), иначе остаётся язык диалога (поле `language` LLM, затем язык клиента) → `customer.language`.
6. Маршрутизация по intent:
   - `OPERATOR_REQUEST`, `COMPLAINT` → handoff (для жалобы — извиниться и передать).
   - `GREETING` (приветствие, которое не распознал шаг 3a: «Здравствуйте, девушки!») → план `GREETING`, тот же шаблон (+ если есть черновик — напомнить, чего не хватает).
   - `FAQ` → ответы только из `faq_items` по `faq_ids` (валидация id) или поиск по ключевым словам; нет совпадений → `NEED_MANAGER` («Мне нужно уточнить эту информацию у менеджера.») + `needs_attention`.
   - **FAQ прежде всего** (16.09.2026, по живым диалогам: «Насколько свежие торты?» приходило как `PRODUCT_QUERY` и выдавало весь каталог): если модель выбрала `PRODUCT_QUERY` без названного товара, `OTHER` или `GREETING`, но есть подходящая запись FAQ (id от модели; для `PRODUCT_QUERY`/`OTHER` — и по ключевым словам), отвечаем `FAQ_ANSWER`, а `OTHER` не считается неудачной попыткой. Промпт понимания требует сопоставлять FAQ по смыслу.
   - **Но ключевые слова не отнимают вопрос у каталога** (21.09.2026, диалог №42): при `PRODUCT_QUERY` без выбранных моделью id запись FAQ, совпавшая **только** по словам наличия (`STOCK_KEYWORDS`: «в наличии», «есть в наличии», «баного», «хастми»…), отбрасывается, если в сообщении есть вопросительное слово `WHICH_WORDS` («какие», «кадом», «намуд»…). «Синнамоны в наличии?» — вопрос про сегодня и отвечается из FAQ, «какие у вас есть в наличии?» — вопрос про ассортимент и отвечается каталогом.
   - **Намерение заказать не съедает вопрос** (21.09.2026, диалог №42): `CREATE_ORDER`/`CHANGE_ORDER` во **вторичных** интентах делает сообщение заказом только если названа позиция (`entities.items`) или есть данные заказа (`_has_order_fields`). «Хочу заказать синнамоны, какие у вас есть?» — это вопрос про ассортимент, а не начало заказа, и бот отвечает списком, а не «что именно хотите заказать?». Первичный `CREATE_ORDER`/`CHANGE_ORDER` работает как раньше.
   - Handoff при недоступности AI (`reason_code=ai_unavailable`) — только «Передаю диалог менеджеру…», без «уточнить эту информацию»: сбой AI ничего не говорит о вопросе клиента.
   - `PRODUCT_QUERY` → факты из каталога (активные товары, цены из БД); неизвестный товар → «такого товара нет в каталоге» + список активных.
   - `CREATE_ORDER` / `CHANGE_ORDER` → шаг 7.
   - `CANCEL_ORDER` → найти черновик/последний активный заказ → по 03 §1.5 → `awaiting="cancel_confirmation"` с вопросом «Отменить заказ №N?» или handoff.
   - `ORDER_STATUS` → последние активные заказы клиента из БД (статус, дата, оплата).
   - `DELIVERY_QUERY` / `PAYMENT_QUERY` → факты из настроек (`delivery_info_text`, `payment_methods_text`, `pickup_address`) + FAQ; нет данных → `NEED_MANAGER`. Именно так бот ведёт себя, пока оплата выключена (03 §3): политики нет, ответы FAQ про предоплату неактивны — вопрос уходит менеджеру, а не получает придуманный ответ.
   - `OTHER` по `other_topic` (новое поле результата понимания): `small_talk` (болтовня, «как дела», «вы бот?») → план `SMALL_TALK` (LLM отвечает по-человечески, факты — только из FACTS); `question` (деловой вопрос, на который нет ответа в каталоге/FAQ/настройках) → `NEED_MANAGER` + `needs_attention` (SPEC §40), неудачной попыткой не считается; `unclear`/null → `failed_ai_attempts += 1`, уточняющий вопрос; при ≥2 — handoff.
7. Оформление заказа:
   1. Черновик: `state.draft_order_id` (статус NEW/WAITING_CONFIRMATION) или `OrderService.create_draft(customer, conversation)` — только когда появилась хотя бы одна позиция/намерение заказа. **Брошенный черновик** (17.09.2026): если черновик не менялся дольше `DRAFT_ABANDON_HOURS` (48 ч) и в сообщении названы новые позиции (`add`/`replace`/`set`), старый черновик отменяется системой (`cancel_reason` «Черновик не завершён клиентом — начат новый заказ», действие `draft_abandoned`) и создаётся новый — «2 коробки», написанные на прошлой неделе, не подмешиваются к сегодняшнему заказу. Сообщение без позиций (дата, адрес, «да») продолжает старый черновик, как раньше (устаревший слот при этом переспрашивается).
   2. Позиции: для каждого `entities.items[]`: `product_id` проверяется в БД (активен, не удалён); иначе `ProductMatcher.match(product_text)` → единственное совпадение → принять; несколько → спросить какой; нет → «нет в каталоге». `quantity=null` → спросить количество («Сколько штук нужно: …?», а для товаров с единицей «кор.» — «Сколько коробочек нужно: …?», факт `pending_items[].unit`). Позиции без названия («2 торта», а для синнамонов — «2 коробки», «синнамоны», «синабоны», «булочки с корицей») → `state.pending_items`, вопрос «какие именно?» (SPEC §11). Общие слова — `CATEGORY_STEMS` в `product_matcher.py`: товары, у которых корень есть в названии или алиасах (с синонимами `CATEGORY_SYNONYMS`: «синабон», «булочк», «кориц» → «синнамон»), а «коробка» — все товары с единицей «кор.» (`PACKAGING_UNITS`). Ответ «2 коробки»/«две коробки» на единственный открытый вопрос «сколько?» — количество этого товара, а не ещё две коробки на выбор (`_quantity_answer`: одно упоминание общего слова с числом, товар входит в его категорию). `items_mode` add/replace/remove/set применяется через `OrderService.update_draft`; `set` в ответ на «какие именно?» работает как `add`. **Угаданный id (18.09.2026):** `product_id` от модели при голом слове категории в `product_text` («синнамон», «2 синнамон», «торт», «коробка», `is_generic_mention`) не принимается — решает `ProductMatcher` (живьём модель на «хамин 2 синнамон» вернула id «Классических синнамонов», и заказ стал 2 классических + два названных вкуса); ответ «две коробки» на вопрос о количестве засчитывается и с угаданным id. Правило 3 промпта понимания говорит то же явно.
   3. Поля: дата/время (валидация 03 §1.3), тип получения, имя, телефон (нормализация), адрес → `DeliveryService.upsert_from_text` → геокодирование синхронно (таймаут 10 с); результат `NOT_FOUND`/`AMBIGUOUS`/`FAILED` → вопрос/кандидаты + ссылка на карту (`LocationRequest`).
   4. `missing = OrderValidator.missing_fields(order)`:
      - не пусто → статус NEW, план `ASK_MISSING` (спрашивать до 2 полей за раз, в порядке списка);
      - пусто → статус `WAITING_CONFIRMATION`, `state.awaiting="confirmation"`, `summary_hash`, план `ORDER_SUMMARY` (детерминированный шаблон SPEC §12).
8. Успешное понимание → `failed_ai_attempts = 0`. Сообщение: `ai_processed=true`, `intent`, `ai_payload`.

Уточнения реализации (этап 5b, покрыты тестами `tests/test_dialog_service.py`):
- **Шаг 3.** `UNCERTAIN` отвечает `CONFIRMATION_REPEAT` без LLM только для «колебания» (`is_hesitation`: маркеры сомнения, «ок»/«👍», пустое сообщение, слишком длинное «да»). Другое сообщение («А как оплатить?») идёт в понимание, ответ дополняется напоминанием «Чтобы подтвердить заказ №N, напишите «Да»». Подтвердить заказ из понимания невозможно — только `YES` на шаге 3. Слово отмены на сводке («отмените заказ») тоже идёт в понимание (`CANCEL_ORDER`), а не в `ASK_WHAT_TO_CHANGE`. Ответ на «Отменить заказ №N?» классифицирует `classify_cancel_confirmation`: здесь «да, отмените»/«бекор кунед» — это `YES`.
- **Голое число** («2», «1 шт», «2 коробки», «2 кор.», «2 қуттӣ») без LLM: выбор варианта адреса (`awaiting=address_choice`) или количество единственного товара из `pending_items` (`quantity`).
- **Вопрос вместе с данными заказа** (17.09.2026): «2 коробки на завтра, а доставка платная?» — `CREATE_ORDER` с `secondary_intents` `DELIVERY_QUERY`/`PAYMENT_QUERY`/`FAQ` (или `faq_ids`) раньше терял вопрос: бот просто задавал следующий вопрос. Теперь `_note_answers` кладёт в факт `answers` ответы из тех же источников, что у отдельных интентов (FAQ по id модели или ключевым словам, `delivery_info_text`/`pickup_address`/`working_hours`, `payment_methods_text`); шаблоны `ASK_MISSING`, `ORDER_SUMMARY` и `ADDRESS_CLARIFY` печатают их первым абзацем, промпт ответа (правило 15) велит ответить сначала на них. Данных нет → `answers.need_manager=true`: «Мне нужно уточнить эту информацию у менеджера.» + `needs_attention`, заказ идёт дальше. **Обратный случай (18.09.2026):** главный интент `FAQ`/`DELIVERY_QUERY`/`PAYMENT_QUERY` с конкретными данными заказа (адрес, дата, время, телефон, получатель — `_has_order_data`; голые `delivery_type`/`payment_method` не считаются: модель ставит их по теме вопроса «доставка есть?») при открытом черновике идёт в поток заказа (`_is_order_message`), а вопрос отвечается через `answers`: «доставка мешава ми? 19-мкр, дом 5, подъезд 2» — адрес сохраняется и геокодируется, ответ про доставку идёт первым абзацем; раньше адрес терялся, и бот потом спрашивал «доставка или самовывоз?».
- **Отклонённый слот** (17.09.2026): если клиент переносит уже полный заказ на день или час, который бот не берёт, прежние дата/время не остаются молча в сводке — отклонённая составляющая очищается и спрашивается заново («На завтра можем не раньше 17:00. К какому времени?»; отклонённый день → «На какую дату нужен заказ?»).
- **Получатель** подставляется (`_default_recipient`) на каждом пути к сводке (`_continue_order`), а не только при разборе полей: имя, поставленное сотрудником в админке между сообщениями, раньше приводило к `order_incomplete` на «ок».
- **Изображение без текста** → handoff («Клиент прислал изображение», 03 §6).
- **Позиции.** Ответ на «какие именно?» распределяет количество из `generic`: один товар получает всё, при N товарах на N штук — по одной (SPEC §11/§12). В режиме `replace` не названное количество = 1 (видно в сводке). Пока есть `pending_items`, спрашиваются только они (как в SPEC §11).
- **Итог и разбивка** (17.09.2026, живой диалог: «5 синамонов, 3 ягодных и 2 фисташковых» превращалось в «ещё 5 на выбор»): общее слово с числом, за которым в том же сообщении названы товары этой категории, — их итог, а не отдельная позиция (`_split_totals`). Сумма совпала — `generic` снимается; вкусы без чисел делят итог как ответ на «какие именно?»; названо меньше — спрашивается только остаток («Записали: Ягодные синнамоны — 3 кор. Подскажите, пожалуйста, какие ещё 2 выбрать?»). Число после товаров («2 ягодных и ещё 3 синнамона») — это ещё 3 на выбор. «Это всё» / «больше ничего» / «хватит» / «бас» (`SmallTalk.DONE`, без LLM) при черновике с позициями снимает открытые «какие именно?» и переходит к следующим вопросам. Комментарий, который повторяет список позиций (два и более «число + товар»: «я же сказал 5 синамонов, 3 ягодных…»), в заказ не пишется; промпт понимания требует в таком случае вернуть позиции заново с `replace`.
- **Дата/время** проверяются (`OrderValidator.slot_problems`) до записи в черновик: прошедшая дата (`delivery_date_past` — «5 августа уже прошло 🙂») / слишком рано (бот называет самый ранний слот: «самое раннее — завтра после 14:00», факты `earliest_*`) / слишком далеко → не записываются, бот называет правило. Если сам день возможен и рано только время («18 сентября к 16:00» при самом раннем 17:00), день записывается, спрашивается только время: «На завтра можем не раньше 17:00. К какому времени?» (`timing_keeps_date`). Если слот «устарел» к моменту «Да», он очищается и спрашивается снова.
- **Получатель доставки** по умолчанию — сам клиент (его имя); `recipient_name` не спрашивается, пока известно или ещё спрашивается имя клиента. Сводка показывает получателя, клиент может исправить.
- **Адрес** геокодируется синхронно (`OrderService.update_fields(request_geocoding=False)` + `GeocodingService`, лестница запросов 03 §7); не `OK` → `ADDRESS_CLARIFY` по статусу: варианты домов (до 3, выбор номером), «нашли улицу/микрорайон, но не дом» + ссылка, «не нашли» + ссылка (формулировка «Адрес записали, но на карте он не нашёлся» — адрес принят, клиенту не говорится, что адреса нет), `FAILED` («проверить не удалось, курьер уточнит») + ссылка + `needs_attention`. К сообщению сразу добавляются следующие вопросы черновика; если больше ничего не нужно — подсказка «напишите «дальше»». Точка клиента на карте ставит задачу `continue_dialog_after_location` → сводка или следующий вопрос; координаты после попытки геокодирования заказ не блокируют (03 §1.3).
- **`OTHER` при открытом черновике** повторяет вопросы черновика (и считается неудачной попыткой: две подряд → handoff).
- **Непредвиденная ошибка** в обработке (баг) → `InboundMessageService` передаёт диалог оператору со стандартным сообщением; клиент не остаётся без ответа.
- **Параллельные сообщения** одного клиента обрабатываются по очереди (`app/core/locks.py`, Redis-блокировка по ключу треда; занято → повтор задачи).

## 6. Ответ клиенту (`responder.py`)

`ReplyPlan = {kind, language, facts: dict, missing_fields: list[str], question_hint: str|None, context: dict}`; `kind ∈ {GREETING, ASK_MISSING, ORDER_SUMMARY, ORDER_CONFIRMED, CONFIRMATION_REPEAT, ASK_WHAT_TO_CHANGE, ORDER_CANCELLED, CANCEL_CONFIRM, CANCEL_KEPT, FAQ_ANSWER, PRODUCT_INFO, ORDER_STATUS_INFO, DELIVERY_INFO, PAYMENT_INFO, ADDRESS_CLARIFY, HANDOFF, NEED_MANAGER, UNKNOWN_PRODUCT, CLARIFY, SMALL_TALK, BLOCKED, ASK_RECEIPT, RECEIPT_RESULT, FOLLOW_UP}` (`CANCEL_KEPT` — «Хорошо, заказ №N не отменяем»; `SMALL_TALK` — спасибо/пока/ок/болтовня, факты `small_talk`, `recent_order`; `ASK_RECEIPT` / `RECEIPT_RESULT` — предоплата и чек, §9; `FOLLOW_UP` — догоняющий вопрос, факт `stage` ∈ {draft, confirmation, receipt}, 03 §6a).

- **Всегда шаблоном** (без LLM): `GREETING` (факт `greeting` — какое приветствие вернуть; с 17.09.2026 заказчик хочет фиксированное «Добрый день! Что желаете заказать?», а не пересказ модели), `ORDER_SUMMARY`, `ORDER_CONFIRMED` (с 17.09.2026 при включённой предоплате — плюс абзац с суммой и кошельком, факт `prepayment`), `CONFIRMATION_REPEAT`, `ORDER_CANCELLED`, `CANCEL_CONFIRM`, `CANCEL_KEPT`, `HANDOFF`, `NEED_MANAGER`, `ADDRESS_CLARIFY` (со ссылкой), `BLOCKED` (фиксированный отказ клиенту из чёрного списка), `ASK_RECEIPT`, `RECEIPT_RESULT` (суммы и номер кошелька — ровно те, что сверялись), `FOLLOW_UP` (бот пишет первым, отвечать не на что — формулировать модели нечего, 03 §6a). `PAYMENT_INFO` и `answers` получают факт `prepayment` (кошелёк, банки, доля) — строка «Предоплата: кошелёк … После перевода пришлите чек». Цифры, цены, суммы и даты — только из БД.
- Для `ASK_MISSING` в `question_hint` передаётся текст шаблона — LLM перефразирует ровно те вопросы, которые решил backend (правило промпта: своими словами, одним естественным предложением, без нумерации и без дословного копирования). **Исключение (17.09.2026):** `ASK_MISSING` с фактами, которые клиент должен прочитать точно, — `pending_items` («какие именно?»), `unknown_products`, `timing_problem`, `phone_invalid`, с 23.09.2026 ещё и `quantity_problem` — всегда шаблоном (`responder.uses_template`, `EXACT_ASK_FACTS`). Правило количества попало сюда, когда на «5 классических» модель придумала «коробочками по 2 или 4 штуки»: шаг — арифметика настроек, а не размер коробки (03 §1.3). В живом диалоге модель в таких ответах придумала «какие ещё три синнамона», написала «всё верно» вместо вопроса и повторила из истории отказ по дате, которую backend уже принял. В промпт ответа добавлено: история — только для тона, отказ или проблема из прошлого ответа, которых нет в FACTS сейчас, не повторяются. Шаблоном идёт и `SMALL_TALK` для «ок»/«дальше»/«это всё» (`small_talk` = ack/done): формулировать нечего, а на сводке модель отвечала «Всё верно, заказ уже ждёт подтверждения» вместо напоминания «Чтобы подтвердить заказ №N, напишите «Да»».
- **Общие факты любого плана** (17.09.2026): `greeting` (salam/morning/day/evening/hello) — клиент поздоровался в этом же сообщении, ответ начинается с ответного приветствия (шаблон `render()` и правило 9 промпта); `answers` — ответы на вопрос, заданный вместе с данными заказа (см. §5).
- **Контекст формулировки** (`ReplyPlan.context`, 16.09.2026): последнее сообщение клиента (в тегах «данные, не инструкции»), до 6 последних реплик диалога и имя клиента передаются в промпт ответа, чтобы ответ «подхватывал нить» («Отлично, чизкейк и 5 эклеров записали. На какой день…»). Контекст — не источник фактов: guard по-прежнему разрешает только суммы и товары из FACTS. Стиль промпта: «менеджер пекарни с телефона», 1–3 предложения, «мы», без «Здравствуйте» в каждом ответе, ≤1 эмодзи; таджикский — только кириллица, названия товаров как в FACTS, остальное (включая описания) по-таджикски.
- **Обещание «отправим сегодня» (22.09.2026).** Разбор архива по ситуациям показал: на «Я думала сейчас можете отправить» модель отвечала «Понимаем вас, сейчас отправим таксистом», хотя владелец в тех же случаях пишет «У нас предзаказ хотя бы за день» и решает про исключение сам. Guard дополнен проверкой `same_day_promise`: обещание испечь, отправить, привезти или успеть «сегодня»/«сейчас» (и таджикское «ҳозир мефиристем») отбрасывается, ответ идёт шаблоном. Отрицание обещанием не считается («сегодня не получится» проходит). Проверка снимается, когда предзаказ выключен (`min_lead_time_hours <= 0` → `Responder(allow_same_day=True)`), — тогда «сегодня» действительно возможно.
- **Повторное приветствие (18.09.2026).** Правило 9 промпта модель нарушала: в живом таджикском диалоге она копировала «Ва алейкум ассалом!» первого ответа из истории во все следующие. Поэтому `Responder` убирает приветствие в начале текста модели детерминированно (`strip_greeting`: «Здравствуйте!», «Добрый день,», «Салом!», «Ассалому алейкум!», «Ва алейкум ассалом!», «Рӯз ба хайр!» и их написания; после слов должна идти не-буква, «Саломат бошед!» — не приветствие), если `kind ≠ GREETING` и факта `greeting` нет, — то есть клиент в этом сообщении не здоровался. Остаток начинается с заглавной; текст из одного приветствия → шаблон (`empty_reply`). Что исправлено, записывается в `Reply.fixes` → `ai_payload.reply.fixes` (`["greeting_removed"]`), событие `ai.reply_fixed`.
- **Цены в тексте модели (18.09.2026).** Модель копировала цену и единицу из FACTS как есть: «100.00 сомонӣ кор.», а «кор» по-таджикски значит «работа». `fix_money` приводит текст к виду шаблонов: «100.00 сомони/сомонӣ» → «100 …» в обоих языках, а в таджикском «сомонӣ кор./шт.» → «сомонӣ / қуттӣ» / «/ дона». Правка делается **после** проверок guard и языка, чтобы подставленное таджикское слово не помогло русскому тексту пройти проверку языка. В `Reply.fixes` записывается `money_format`.
- **Таджикский — худжандский регистр (18.09.2026).** Клиенты пекарни — из Худжанда и пишут на северном диалекте; книжный таджикский в ответах читается как чужой. Шаблоны `templates.py` (TG) переписаны в разговорном северном регистре: «раҳмат» (не «ташаккур»), «тайёр» (не «омода»), «нависед» (не «бигӯед»), «пагоҳ», «ҳозир» (не «ҳоло»), «мебахшед» (не «бубахшед»), «Саломат бошед!» на «спасибо», бытовые заимствования «адрес», «доставка», «курер», «чек», «перевод», «квартира», «ориентир», «микрорайон» (не «суроға», «интиқол», «хаткашон», «ҳуҷра», «нишона»), вопросы «Расонем ё худатон мегиред?», «Чандто лозим: …?», «Фармоиш барои кадом рӯз лозим?»; сводка — «Фармоишатонро тафтиш кунед:», подтверждение — «Раҳмат! Фармоиши №N тасдиқ шуд ✅». Промпт ответа получил раздел TAJIK (правила 17–18): тот же регистр и список слов; вопросы из QUESTION HINT в таджикском сохраняются почти дословно, по одному короткому предложению на вопрос, без склейки двух вопросов в одно предложение (модель склеивала их в неграмотную фразу). Промпт понимания получил словарь диалекта (правило 14, KHUJAND DIALECT): «-даги» (мекадаги = хочет), «-ба» (манба = ба ман), «-а/-я/-ва» вместо «-ро» (числава), «кати» = «бо», «-ми» — вопрос, «якта/дута», «чанд пул», «пагоҳ/пагоҳӣ/бегоҳ/пешин/ҳозир», «боша/майлаш/нағз», «ака/апа», «19 число», русские слова внутри таджикской фразы. Детерминированные списки (`confirmation.py`, `small_talk.py`, `language.py`) дополнены теми же формами (03 §5). Проверка носителем языка остаётся открытым вопросом 4 (PROGRESS).
- **Настройка по архиву Instagram (21.09.2026).** Выгрузка переписки самой пекарни (224 диалога, 31.08–18.09.2026) использована для настройки детерминированных частей: в промпт понимания (правило 14) добавлен словарь слов, которые клиенты пишут чаще всего («баного» = сейчас/в наличии, «хайми/хастми», «донаш», «чан пул», «намуд», «каропка», «партоид/гузашт» = перевёл, «худам мегирам» = самовывоз, латиница целыми сообщениями); примеры few-shot переписаны с тортов на реальный ассортимент (самое частое сообщение — «Сколько стоит коробка?»); в правило 12 добавлены факты `delivery_closed_day` и `quantity_problem` (03 §1.3). Словари `language.py` дополнены теми же формами (кириллица и латиница), `product_matcher.py` — написаниями упаковки («каропка», «куттӣ», «бокс»): слово «коробка» само по себе не называет вкус, поэтому при каталоге с ценой за штуку оно даёт весь каталог и вопрос «какие именно?», а не «такого товара нет».
- Проверка ответа LLM дополнена проверкой языка: ответ не на языке плана → шаблон; проверка строгая (`decisive_letters=False`, названия товаров и тексты FACTS не считаются): русская фраза с «200 сомонӣ» — не таджикский ответ. Арабская/персидская и прочая чужая письменность в ответе → `foreign_script` → шаблон. Разрешённые суммы — денежные поля FACTS и числа внутри текстов FACTS (например, стоимость доставки из настроек), но не части дат/времени.
- Остальные — LLM (`complete_text`) с системным правилом «используй только факты из FACTS; не упоминай цены/товары/наличие/адреса, которых нет в FACTS; язык — {language}; коротко, дружелюбно, можно 1 эмодзи». Затем `ResponseGuard`:
  - все числа рядом с `сомони|смн|TJS|сом` должны входить в множество цен/сумм из facts;
  - запрещённые обещания («подтвержден», «заказ принят», «тасдиқ шуд») допустимы только для `ORDER_CONFIRMED`;
  - длина ≤ 1000 байт UTF-8 (лимит Instagram) — иначе разбить на части по абзацам.
  - Нарушение или ошибка LLM → детерминированный шаблон того же `kind`.
- Шаблон сводки (RU):
  ```
  Проверьте, пожалуйста, заказ:

  Красный бархат — 1 шт.
  Медовик — 1 шт.

  Время: 18:00
  Доставка: да            | Самовывоз: {pickup_address}
  Адрес: {address}        (только доставка)
  ```

## 7. Tools (SPEC §39, `tools.py`)

| tool | тип | исполнение |
|---|---|---|
| `get_products()` | read | активный каталог |
| `get_product(product_id)` | read | |
| `get_customer()` | read | текущий клиент диалога (id берётся из контекста, не из аргумента) |
| `get_order(order_id)` | read | только заказы **этого** клиента |
| `get_customer_orders()` | read | последние 10 заказов клиента |
| `calculate_order_total(items)` | read | цены из БД |
| `get_delivery_info()` | read | настройки доставки/самовывоза/оплаты |
| `create_order_draft(...)`, `update_order_draft(...)`, `confirm_order(order_id)`, `cancel_order(order_id)`, `request_operator(reason)` | write (proposed) | LLM их **не исполняет**: они описаны в схеме как намерения; фактическое исполнение — `DialogService` по алгоритму §5 с проверками (confirm — только при `classify_confirmation == YES`) |

Read-tools передаются LLM на этапе понимания (в дополнение к уже вложенному контексту, `strict: true`, не более 2 раундов); `ToolRegistry(db, ToolContext(customer, conversation)).execute(name, args)` исполняет только read-tools и проверяет принадлежность данных клиенту; ошибки возвращаются моделью как данные (`{"error": ...}`). Write-tools — методы `ToolRegistry`, через которые `DialogService` делает все записи бота: они повторно проверяют, что заказ принадлежит клиенту диалога, а `confirm_order`/`cancel_order` требуют решения `ConfirmationDecision.YES`. Дополнительно `record_change_request` пишет в журнал просьбу изменить оформленный заказ (03 §1.5).

## 9. Чек об оплате (`receipt.py`, 17.09.2026)

Заказчик временно просит предоплату на свой счёт (кошелёк-телефон в Душанбе Сити / Алиф / Эсхата либо номер карты) и хочет, чтобы бот сам открывал присланный чек. Правила — 03 §3; здесь — как это устроено.

- **Модель только читает.** `read_receipt(llm, image_bytes, media_type)` → `complete_json` с системным промптом `RECEIPT_RULES` (ничего не угадывать; сумма получателю без комиссии; получатель как напечатан, в том числе с маской; статус `success` только при явной отметке об успехе; `is_receipt=false` для любой другой картинки) и одним user-сообщением из картинки и текста. Картинка — блок `{"type": "image", "source": {"type": "base64", "media_type", "data"}}` (`llm_client.image_block`): Anthropic принимает его как есть, `GeminiLLMClient` превращает в `inlineData`. Ответ проходит `parse_reading`: сумма «12 000,50» → `Decimal`, статус из перечня, уверенность 0..1, тексты обрезаны.
- **Решение — в Python** (`check_receipt(reading, expected, wallet)`): `not_receipt` (не чек или `confidence < 0.5`) → картинка оператору; `status` (failed/pending); `currency` (валюта названа и это не сомони); `wallet_mismatch` — `wallet_matches`: цифры получателя сравниваются с хвостом нашего номера, символы маски `*`/`x`/`•` — подстановочные, «+992 92 *** 53 33» и «92 *** 53 33» совпадают с +992 92 757 53 33, «5058 27** **** 6297» и «**** 6297» — с картой 5058 2703 8115 6297, другой номер — нет; 13+ цифр у получателя, когда наш счёт — кошелёк-телефон (`is_card_number(wallet)` ложно), означают чужую карту или счёт → `False`; только имя или меньше 4 цифр → `None` (не блокирует, оператор сверит); `amount_unknown`; `amount_short` (меньше `expected_prepayment(total, paid, percent)`). Без проблем → `ok`.
- **Что происходит дальше** (`DialogService._receipt`): строка в журнале заказа (`OrderService.record_receipt`, «Чек из Instagram: 300.00 сомони, Alif Mobi, получатель совпадает, 17.09.2026 14:05. Сверьте поступление…»), `needs_attention`, `Message.ai_payload = {"receipt": {reading, ok, problems, amount, expected, shortfall, wallet_ok}}`, клиенту — `RECEIPT_RESULT` (первая по важности проблема: статус → валюта → получатель → сумма не разобрана → не хватает → ок; слово «кошелёк» или «карта» в текстах выбирает `templates._account_words` по нашему номеру). `prepayment_auto_confirm=true` и `ok` → `PaymentService.register_payment(PAYMENT, TRANSFER, actor=AI)`, текст «оплату получили ✅». Сбой модели → handoff «Клиент прислал чек об оплате, распознать его не удалось».
- **Подлинность** (18.09.2026, правила — 03 §3). Модель при чтении дополнительно переписывает дату в `paid_at_iso` («YYYY-MM-DDTHH:MM», день первым в числовых датах); остальное решает Python:
  - повтор: `file_digest` (SHA-256 файла), `normalize_reference` (номер операции), `transfer_fingerprint` (сумма + минута + отправитель) → `ReceiptRepository.find_earlier` → `EarlierReceipt(order_id, same_order, match)` → проблема `duplicate` (другой заказ) или `resent` (этот же);
  - даты: `paid_at_bounds` (бизнес-часовой пояс; дата без времени — весь день) → тревоги `date_future` / `date_before_order`;
  - доплата: `credited_amount(paid_amount, прежние чеки заказа)` — засчитываются только чеки без проблем, кроме `amount_short`;
  - **следы правки — отдельный вызов** `inspect_receipt` (`INSPECTION_RULES`, стадия `receipt_inspection`, JSON `{lines, mismatch, where}`): модель описывает, каким шрифтом, цветом и на каком фоне нарисована каждая строка, и отмечает значение, нарисованное не так, как остальные. Только для распознанных чеков; сбой вызова не мешает приёму чека (без подсказки). Почему отдельный: проверено вживую на синтетической подделке (сумма «1500,00 TJS» шрифтом с засечками на заплатке) — поле `looks_edited` внутри промпта чтения Gemini flash-lite и flash пропустили 3 из 3 раз, отдельный узкий вопрос поймал 3 из 3 и ни разу не придрался к оригиналу. Аккуратную подделку тем же шрифтом так не поймать — для этого приложение банка.
  - тревоги (`date_*`, `looks_edited`) в `verdict.alerts`, клиенту не попадают (`RECEIPT_RESULT` смотрит только на `problems`); `ok=false` → автоотметки нет; оператору — «ВНИМАНИЕ: …» в журнале заказа; каждый распознанный чек — строка `payment_receipts` (02).
- **Проверено вживую** (17.09.2026, Gemini, синтетический скриншот Alif Mobi): прочитаны сумма «300,00 TJS», статус «Перевод выполнен», получатель «+992 92 *** 53 33» с именем, отправитель, дата и номер операции; сверка сошлась.
