**17.09.2026 — ревизия ключевых узлов бота.** Заказчик: «пройдись по всем важным местам, что можно
улучшить, всё ли работает на 100%». Прочитан весь конвейер (`dialog_service`, `confirmation`,
`small_talk`, `product_matcher`, `understanding`, `prompts`, `templates`, `responder`, `guard`,
`order_validator`, `order_pricing`, адреса/геокодер, `inbound`/`messaging`, Instagram-клиент и webhook,
Gemini/Anthropic-клиенты). Без замечаний: подтверждение только через `classify_confirmation`, отмена,
handoff по ключевым словам и при сбое LLM, чёрный список, язык, guard (суммы/товары/подтверждения/
чужая письменность), 24-часовое окно, разбиение длинных сообщений, идемпотентность webhook.
Найдено и исправлено (все — по сценариям, которые в живом диалоге ломают заказ):
1. **Поправка количества одного товара** («нет, ягодных 3») — раньше модель выбирала либо `add`
   (позиция удваивалась: 2+3=5), либо `replace` (остальные товары пропадали). Новый `items_mode=set`
   (`OrderPricing._set`, схема понимания, правило 9 промпта): названные товары получают ровно это
   количество, остальное не трогается; в ответе на «какие именно?» `set` работает как `add`.
2. **Вопрос вместе с данными заказа** («2 коробки на завтра, а доставка платная?») терялся — бот просто
   задавал следующий вопрос. Теперь `_note_answers` → факт `answers` (FAQ по id модели, доставка,
   оплата из настроек) печатается первым абзацем в `ASK_MISSING`/`ORDER_SUMMARY`/`ADDRESS_CLARIFY` и
   передаётся модели (правило 15 промпта ответа); нет данных → «уточню у менеджера» + `needs_attention`.
3. **Приветствие внутри сообщения** («Здравствуйте, хочу 2 коробки», «Салом, …») оставалось без ответа
   (шаблоны выбора позиций и правило «не здороваться» в промпте). Теперь `_finish` кладёт `greeting` в
   факты любого плана, `render()` начинает ответ с «Здравствуйте! …»/«Салом! …», промпт — правило 9.
4. **Отклонённый слот у полного заказа**: «лучше 18-го к 12:00» при самом раннем 17:00 — старые дата/
   время молча оставались в сводке. Теперь отклонённая составляющая очищается и спрашивается заново.
5. **«2 коробки» на вопрос «сколько?»** превращалось в ещё две коробки на выбор; вопрос звучал «Сколько
   штук нужно» для товаров, продающихся коробочками. Голое число принимает «2 кор./коробки/қуттӣ», через
   модель `_quantity_answer` записывает количество в ожидающий товар; шаблон «Сколько коробочек нужно:
   …?» (факт `pending_items[].unit`, TG «Чанд қуттӣ лозим аст»).
6. **Брошенный черновик**: «2 коробки», написанные на прошлой неделе, подмешивались к сегодняшнему
   заказу. Черновик, не менявшийся 48 ч (`DRAFT_ABANDON_HOURS`), при новых позициях отменяется
   системой («Черновик не завершён клиентом — начат новый заказ»), сообщение без позиций продолжает его.
7. **Получатель по умолчанию** подставлялся только при разборе полей: имя, поставленное сотрудником
   в админке между сообщениями, давало `order_incomplete` на «ок» → аварийный handoff. Теперь
   `_default_recipient` на каждом пути к сводке.
8. Промпт понимания: товар латиницей («korobka», «tort») → `product_text` кириллицей, иначе «нет в
   каталоге».
Проверка: короткий диалог через настоящий конвейер (Gemini) на копии `dev.db`: «Здравствуйте, хочу
2 ягодных и 3 классических, а доставка платная?» → «Здравствуйте! Записали… Доставка по Худжанду
стоит от 20 до 40 сомони… На какую дату…»; «нет, ягодных 3» → модель вернула `set`, в черновике
3+3; «и ещё фисташковые» → «Сколько коробочек нужно: Фисташковые синнамоны?»; «2 коробки» → без
модели 2 кор.; сводка на 800 сомони. Тесты: `test_scenarios_bot.py` (раздел «review of 17.09.2026»,
9 сценариев), `test_order_pricing.py` (`set`), обновлены ожидания приветствия в 4 старых тестах.
2224 теста проходят. Контракт: 05-ai.md §3, §5 (3a, 7.1, 7.2, уточнения), §6; 03-business-rules.md
§1.4, §1.5.

**17.09.2026 — разбор живого тестового диалога: количества, повторы, адреса.** Заказчик: «бот путается в
количествах, переспрашивает одно и то же, пишет «нет такого адреса», хотя адрес есть». Разбор диалога
(webtest, 11:09–11:17) и исправления:
1. «Хочу заказать 5 синамонов, 3 ягодных и 2 фисташковых» → понимание вернуло 3 позиции (5 «синнамонов»
   без вкуса + 3 + 2), бот записал 3+2 и спрашивал «какие ещё». Теперь `_split_totals` в
   `dialog_service.py`: число перед вкусами этой категории — их итог; правило 8/9 промпта понимания.
2. Ответы `ASK_MISSING`, сформулированные моделью, врали: «какие ещё три», «всё верно» вместо вопроса,
   и главное — повтор отказа по дате, которую backend уже записал (скопирован из истории). Теперь
   такие вопросы (выбор позиций, неизвестный товар, проблема даты, неверный телефон) — всегда шаблоном
   (`responder.uses_template`), в шаблоне «Записали: …» + «какие ещё N выбрать?»; простые вопросы по
   полям модель формулирует как раньше. Правило 5 промпта ответа: не повторять из истории то, чего нет
   в FACTS.
3. «Я же сказал всего 5 синамонов…» ушло в комментарий заказа и попало в сводку — комментарий, который
   повторяет список позиций, больше не пишется; промпт: повтор/исправление списка → позиции с `replace`.
4. «Все на этом» уходило в модель и снова спрашивалось «какие именно» — `SmallTalk.DONE` («это всё»,
   «больше ничего», «хватит», «бас») без LLM снимает открытые вопросы выбора.
5. «18 сентября на 16:00» при самом раннем 17:00 отклонялось целиком — теперь день записывается, бот
   пишет «На завтра можем не раньше 17:00» и спрашивает только время.
6. Адрес «28 микрорайон дом 76» — NOT_FOUND. Причины: запросы в форме Душанбе «28-й микрорайон» (в OSM
   Худжанда такие названия дают чужие микрорайоны), и при втором адресе геокодировались **старые**
   разобранные части (микрорайон 28, дом 76). Живая проверка Nominatim/Overpass: в Худжанде ~12 тыс.
   домов в OSM, дома в микрорайонах подписаны «31 мкр» и т. п. Лестница теперь «N мкр, дом» → «N
   микрорайон» → «N мкр» (дом 31 мкр/28 и 20 мкр/28 находятся точно; дома 28 мкр/76 в OSM нет —
   «нашли 28 микрорайон, но не дом» + ссылка), новый адрес сбрасывает части старого. Текст «не нашли»
   смягчён: «Адрес записали, но на карте он не нашёлся…».
7. Ссылка «отметьте точку на карте» вела на `localhost:3000` — в `backend/.env` (не в репозитории)
   `FRONTEND_PUBLIC_URL` указан на ngrok-адрес демо.
8. «Ок»/«дальше»/«это всё» (`SMALL_TALK` ack/done) — шаблоном: на сводке модель писала «Всё верно, заказ
   уже ждёт подтверждения».
Проверка: диалог заказчика прогнан заново через настоящий конвейер (Gemini + Nominatim) на копии
`dev.db` — позиции 3+2 записаны сразу, комментария нет, день сохранён при раннем часе, «все на этом»
не зацикливается, адрес — «нашли 28 микрорайон, но не дом» со ссылкой на ngrok. Тесты:
`test_scenarios_bot.py` (итоги, остаток, «это всё», комментарий, дата с замороженным временем, лестница и
сброс частей адреса), `test_ai_responder.py`. 2215 тестов проходят.

**17.09.2026 — настоящий ассортимент «Синнамонов» вместо демо-тортов.** По скриншотам Instagram
заказчика (профиль и 7 постов): синнамоны продаются коробочками по 4 штуки одного размера, вкусы —
классика, шоколад, ягоды, фисташка, яблоко, плюс ассорти «Палитра вкуса» (классика, шоколад, ягоды,
фисташка в одной коробочке; заказчик подтвердил, что это отдельный товар). **Цен в постах нет** —
заказчик выбрал временную цену для теста: все 6 коробочек по 100 сомони, единица «кор.», в описании
«Цена временная — для теста.» (бот называет её клиентам). Настоящие цены заказчик выставит в «Товарах»
— это открытый вопрос. `scripts/seed_demo.py` (`PRODUCTS` через `_box`) и `scripts/faq_data.py`
переписаны: из FAQ убраны вопросы только про торты (дизайн по фото, надписи, вес, свадебные/детские),
добавлены «Какие вкусы», «Какой вкус выбрать», «Сколько в коробочке», «Разные вкусы в одной
коробочке», упаковка, фото в актуальных «Синнамоны»/«Виды», акции в «Акции»; политика (хранение,
предоплата, доставка) по-прежнему выдуманная демо-политика, её проверяет заказчик. Чтобы бот понимал
новый каталог: `product_matcher.py` — общие слова «синнамоны/синабоны/булочки с корицей» и «коробка»
(все товары с единицей «кор.») дают вопрос «какие именно?», а не «такого товара нет»;
`confirmation.py` — вкусы в ответе на сводку («Да, фисташковые») — это детали (`CHANGE`), а не «Да»;
`templates.py` — «кор.» по-таджикски «қуттӣ», в строке товара больше нет «шт.. Описание»; пример в
правиле 14 промпта понимания про «Самбуса с мясом» заменён на синнамоны. Рабочая `dev.db` обновлена
разовым скриптом (не в репозитории): 11 демо-товаров мягко удалены (история заказов хранит названия),
6 коробочек добавлены, FAQ синхронизирован (31 запись, правки владельца не трогались бы), резервная
копия базы сделана перед изменением. Тесты: `test_product_matcher.py` (коробки, синонимы, вкусы),
`test_confirmation.py`, `test_ai_responder.py` (строки товара, таджикская единица).

**17.09.2026 — ответ на приветствие.** По просьбе заказчика на «Добрый день» бот отвечает «Добрый день!
Что желаете заказать? 😊» — всегда одинаково и без LLM. Сообщение только из приветствия распознаётся
в `app/ai/small_talk.py` (`SmallTalk.GREETING`, `detect_greeting` → `Greeting`: salam/morning/day/
evening/hello) до вызова модели; ответ — тем же приветствием («Доброе утро», «Добрый вечер»,
«Ассалому алейкум» → «Ва алейкум ассалом», «Салом»/«Рӯз ба хайр» по-таджикски, прочее →
«Здравствуйте»). `ReplyKind.GREETING` перенесён в `TEMPLATE_KINDS` (раньше формулировала модель:
«Здравствуйте! Чем можем помочь?»), в том числе когда GREETING пришёл из понимания («Здравствуйте,
девушки!»). При открытом черновике вместо «Что желаете заказать?» идут его вопросы или напоминание
подтвердить заказ. Попутно исправлен подсчёт слов-заполнителей в `detect_small_talk`: «ба» внутри
фразы «рӯз ба хайр» больше не «прощает» лишнее слово. Приветствие с вопросом («Добрый день, сколько
стоит?») по-прежнему идёт в понимание, и отдельного «Добрый день» в ответе там нет (правило 9 промпта
ответа). Тесты: `test_scenarios_bot.py` (сценарии и детекторы), `test_ai_responder.py` (шаблон);
тесты, где «Здравствуйте» служило поводом вызвать LLM, переведены на вопрос.

## 2. Ключевые решения (и почему)

- **Sync SQLAlchemy 2.x + psycopg3.** Нагрузка малая, Celery синхронный, нет проблем с lazy load в async.
- **Тесты на SQLite in-memory.** Enum хранятся как VARCHAR+CHECK (`native_enum=False`), поэтому схема переносима. Опционально тесты гоняются и на PostgreSQL (`TEST_DATABASE_URL`).
- **LLM: Anthropic SDK, модель `claude-opus-5`** (env `LLM_MODEL`), `effort=medium`, структурированный вывод через `output_config.format`, серверные fallbacks при отказе. Двухшаговый конвейер: *понимание* (JSON) → детерминированный `DialogService` → *ответ*. Сводку заказа, подтверждение и суммы формируют шаблоны, а не LLM (`docs/architecture/05-ai.md`).
- **Подтверждение заказа** определяет только детерминированный классификатор (`03-business-rules.md` §5). Фразы «ну вроде», «наверное» и подобные заказ не подтверждают.
- **Новый / постоянный клиент.** Постоянный — тот, у кого есть хотя бы один заказ в статусе `COMPLETED` (SPEC §16). Снимок признака хранится в `orders.is_repeat_customer` при подтверждении.
- **Статистика и отчёты** по умолчанию считаются по `delivery_date`. Учитываются статусы CONFIRMED…COMPLETED.
- **Instagram**: «Instagram API with Instagram Login», `graph.instagram.com/v25.0`.
  - Текст сообщения — не более 1000 байт UTF-8.
  - Действует 24-часовое окно ответа.
  - Webhook-события дедуплицируются по `mid`.
  - **Риск**: не подтверждено, что при Standard Access можно отвечать внешним пользователям. Проверить в первый день реальным аккаунтом.
- **Maxim**: официального API нет (вердикт C). Не подтверждено, что Maxim работает в Душанбе (на сайте только Бустон и Худжанд). Реализуется только `ManualMaximIntegration`: оператору формируется копируемая карточка и список в порядке маршрута. Автоматизация Android-приложения — вне MVP, только документ.
- **Голос**:
  - STT — ElevenLabs Scribe v2. Таджикский поддерживается с оценкой «Good».
  - TTS — OpenAI `gpt-4o-mini-tts`, только для русского. Таджикского TTS нет ни у одного облачного провайдера, поэтому таджикоязычным клиентам ответ только текстом.
  - Голосовые ответы по умолчанию выключены.
- **Геокодирование**:
  - По умолчанию Nominatim: координаты можно хранить (ODbL).
  - Google — опционально, с лицензионными ограничениями (хранение не более 30 дней, нельзя показывать на не-Google карте).
  - Основной надёжный источник координат — точка, которую клиент отметил сам по ссылке `/l/{token}`. Автопринятие адреса — только если найден ровно 1 кандидат уровня «дом» внутри bbox города.
- **Маршрут**: матрица расстояний из OSRM (опциональный профиль compose `routing`) или оценка haversine. Решатель локальный: полный перебор при n ≤ 8, иначе nearest neighbour + 2-opt + Or-opt. Опоздание сверх окна `delivery_time ± 60 мин` штрафуется.
- **Frontend**: Next.js App Router + Tailwind, React Query, recharts, react-leaflet. Запросы идут на `/api`, rewrites проксируют их на backend. Access token хранится в памяти, refresh token — в localStorage.

## 4. План следующих этапов (как делить работу)

Работа ведётся параллельными треками с **непересекающимися файлами**. Каждый трек пишет свои тесты в отдельный файл. После каждого трека — независимая проверка на соответствие контракту и прогон тестов.

**Этап 3 — backend-домены.** Этапы 3 и 4 идут одновременно: frontend опирается только на контракт `04-api.md`.
- **Волна 0** (один агент, до остальных):
  - все репозитории `app/repositories/*`;
  - `SettingsService` + схема `BusinessSettings`;
  - ядро `DeliveryService` (`upsert_for_order`, `remove_for_order`, применение координат, копирование адреса в заказ) без геокодирования.
- **Волна 1** (параллельно; каждый трек: service + schemas + routes + tests, у каждого трека свои файлы):
  1. auth и users (refresh-ротация, rate limit на логин);
  2. products, faq, settings API (статус интеграций);
  3. customers и orders:
     - `OrderService`: переходы, `OrderValidator`, pricing;
     - `PaymentService`, журнал `OrderEvent`;
     - `CustomerService.recalculate_status`, нормализация телефона;
  4. statistics, production, reports (текст отчёта строго по SPEC §22; beat-задача `maybe_generate_daily_report`);
  5. deliveries:
     - `GeocodingService` + адаптеры Nominatim/Google;
     - `LocationRequest` и публичные эндпоинты;
     - `route_optimizer.py` + `RouteOptimizationService`, OSRM/haversine;
     - `ManualMaximIntegration`, dispatch-sheet.
- После каждого трека — независимая проверка на соответствие контракту и тесты.
- Conversations API перенесён в этапы 5–6: ему нужна отправка через Instagram.

**Этап 4 — страницы админки** (по трекам, только `tsc` и `lint`; финальный `npm run build` — один раз в конце):
